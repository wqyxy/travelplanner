# AI 旅行计划网页版产品方案

> 状态：**当前目标产品定义 / 产品需求最高依据**  
> 更新日期：2026-09-05  
> 本文件只定义产品与用户体验，**不是施工方案，也不定义技术实现**。  
> 当前代码仍基于既有五步实现；新的技术修改方案应在本产品方案确认后另行编写。  
> UI 规范：[`五步 UI 交互规范.md`](./五步%20UI%20交互规范.md)（文件名为历史兼容，内容已更新为“最终线路”版）

# 1. 产品定位

TravelPlanner 是一个以 **最终线路 + 地图 + 右侧唯一控制台** 为核心的结构化 AI 旅行规划工作台。

它不是一次性生成攻略的聊天机器人，也不要求用户按一串工程步骤维护多份互相同步的计划。

产品最高原则：

> **用户是旅行方案的唯一决策者，AI 负责生成、补充、解释和优化，但不能在未授权时替用户改掉已经排好的线路。**

系统可以提醒路线过长、时间紧张、地点未定位或安排不合理，但这些默认属于提醒，而不是阻止用户保存或手工调整的理由。

地图 Provider 负责可信的地图事实，例如坐标、Provider Place ID、真实路线 geometry、距离与时长。AI 不伪造这些事实。

---

# 2. 产品结构：从五步收敛为两个核心工作区

用户不再面对：

```text
1 旅行需求
2 想去哪些地方
3 路线和天数
4 补充景点
5 每日行程
```

新的产品结构只有两个主要工作区：

```text
规划：旅行需求
行程：最终线路
```

其中：

- **旅行需求**：填写整趟旅行的基础输入。
- **最终线路**：承载主要地点、住宿分界、详细景点、每日线路、交通、地点状态和后续所有高频调整。

原 Step 2“地点”和原 Step 4“补充景点”不再有独立页面；它们变成“最终线路”里的两种生成能力。

原 Step 3“路线和天数”和原 Step 5“每日行程”不再维护两套计划；它们合并为同一份最终线路的不同精细程度。

用户完成初次规划后，日常最常回到的页面应该是 **最终线路**。

---

# 3. 唯一产品事实：最终线路是一份有序地点列表

最终线路是整趟旅行唯一需要用户理解的线路事实。

概念上：

```text
地点 A
↓
地点 B
↓
地点 C
↓
地点 D
...
```

每个地点在列表里都有稳定的相对顺序。地点可以是城市、景区、机场、餐厅、观景点、酒店或其他真实地点；用户不需要理解 Planning Area、Core Visit、Detail Interest、Skeleton、Macro / Detail 等内部概念。

最终线路负责表达：

```text
地点顺序
地点是否当前参与行程
哪些位置形成住宿 / 日程分界
地点之间的交通关系
详细景点在整条线路中的位置
```

Day、地图路线和各种汇总都应该从这份最终线路派生，而不是再成为另一份需要和它同步的产品数据。

---

# 4. 地点状态：正常 / 待定 / 不去

最终线路中的地点不因为“待定”或“不去”而离开列表。

地点有三种用户可理解的状态：

```text
正常
待定
不去
```

主地点卡右侧只保留两个偏好按钮：

```text
待定
不去
```

同时保留：

```text
编辑
移除
```

规则：

- **正常**：参与当前实际线路、日程和路线计算。
- **待定**：仍保留在线性排序中，卡片变为深灰色，不参与当前路线和日程计算。
- **不去**：仍保留在线性排序中，卡片以另一种深灰状态显示，不参与当前路线和日程计算。
- 待定 / 不去都不是删除；恢复为正常时，直接回到原来的排序位置，不需要 AI 再决定插入位置。
- **移除**才是真正从最终线路列表移除。

“待定”和“不去”的视觉要有区别，但都弱化于正常地点。

不再要求普通用户维护“必去 / 想去 / optional / excluded”这套多级偏好按钮。

---

# 5. 地图同时显示所有最终线路地点

地图的地点来源只认最终线路列表。

无论地点是：

```text
正常
待定
不去
```

只要它仍在最终线路列表中，就应在地图上显示。

地图用状态颜色区分：

- 正常地点：正常主视觉。
- 待定地点：灰色状态 A。
- 不去地点：灰色状态 B，与待定可明显区分。

但是实际交通路线只连接 **正常状态** 的地点。

例如最终线路排序是：

```text
A
X（待定）
B
Y（不去）
C
```

地图显示 A、X、B、Y、C 五个地点；当前真实路线按：

```text
A → B → C
```

计算。

---

# 6. 第一次生成：在最终线路里生成主要住宿地点

原 Step 2 的生成能力移入“最终线路”。

用户第一次生成时，AI 先生成整趟旅行的 **主要住宿 / 停留地点骨架**，并直接按照建议顺序放进最终线路。

这一批主要地点不是独立候选池，也不需要用户再进入另一个步骤把它们“采用”到线路中。

重要规则：

> **生成主要地点不等于给每个地点默认“住 1 晚”。**

“住几晚”不作为地点上的独立属性存在，也不使用 `stayDays` 这样的用户概念。

初始旅行有多少天、在哪里形成住宿分界，应直接体现在生成出来的日程块 / 线路分界中。如果一个地点连续停留多天，由多个连续日程块表达，而不是在地点上存一个“住 2 晚 / 住 3 晚”的数字。

---

# 7. 住宿不是地点类型，而是日程分界

一个地点是什么，与“这里是否结束一天”是两件事。

产品上可以理解为：

> **住宿分界把一条连续线路切成一天一天。**

所有日程都是线性的、已经排好顺序的。

例如有效线路：

```text
奥克兰
→ 霍比屯
→ 罗托鲁瓦【住宿分界】
→ Wai-O-Tapu
→ 陶波
→ 惠灵顿【住宿分界】
```

自然得到：

```text
Day 1：奥克兰 → 霍比屯 → 罗托鲁瓦
Day 2：罗托鲁瓦 → Wai-O-Tapu → 陶波 → 惠灵顿
```

核心规则：

> **两个连续住宿分界之间的所有有效地点，都属于同一个日程块。**

系统不因为距离太远、一天不合理或路线奇怪而自动拆分用户手工排好的日程。

---

# 8. “住 / 多一晚 / 不住”直接修改日程块

用户不编辑“住几晚”字段。

住宿相关动作直接作用于最终线路和日程分界：

### 多一晚

在当前地点增加一个新的日程块。

例如：

```text
Day 3：A → 陶波
Day 4：陶波 → B
```

用户在陶波“多一晚”后可以变成：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

新增加的 Day 可以暂时没有详细景点，之后再由用户或 AI 补充。

### 不住

取消该地点作为住宿分界。该地点本身仍可以是正常线路地点；取消分界后，相邻日程自动合并。

例如：

```text
Day 1：A → B【住】
Day 2：B → C → D【住】
```

把 B 改为“不住”后，机械变成：

```text
Day 1：A → B → C → D【住】
```

系统不能因为这样“不合理”而偷偷重新排地点。

注意：

- **不住**：地点仍然去，只是不再作为当天结束点。
- **不去**：地点暂时不参与实际线路，但仍保留在最终线路排序和地图中。

两者语义必须严格分开。

---

# 9. 第一日、最后一日与多日停留

第一日：

> 从旅行起点开始，到第一个有效住宿分界结束。

起点可以是机场、城市、酒店、租车点或其他地点，不要求它本身是住宿点。

最后一日允许没有住宿。例如：

```text
皇后镇【上一晚住宿】
→ 箭镇
→ 皇后镇机场【旅行结束】
```

这就是最后一个 Day，不需要为了凑结构而再制造住宿点。

同一个地点连续停留多日时，不保存“住几晚”的地点属性；直接用多个连续日程块表达。后续可以自然把不同的详细地点插入这些 Day。

Day 1、Day 2、Day 3 等编号始终按当前有效住宿分界和旅行终点自动连续显示。用户改变住宿分界后，编号立即重新计算。

---

# 10. 手工排序优先于“合理性”

手工调整是产品最高优先级的线路事实。

用户可以：

```text
拖动地点顺序
设置 / 取消住宿分界
增加一天
把地点设为待定
把地点设为不去
恢复地点
编辑地点
移除地点
```

系统只执行用户明确要求的结构变化。

即使用户手工形成：

```text
一天跨越非常远的距离
地点顺序明显绕路
一天包含很多地点
```

也允许保留。

系统可以显示提醒，但不能自动优化。

只有用户明确点击或提出：

```text
让 AI 优化
优化这一天
优化这一段
优化全程
```

AI 才获得重新排列相关范围的权限。高影响优化应先让用户看清变化再应用。

---

# 11. 第二次生成：在最终线路里“生成详细地点”

原 Step 4“补充景点”取消独立页面。

最终线路已有主要住宿地点和日程结构后，用户在同一页面点击：

```text
生成详细地点
```

AI 生成原 Step 4 负责的景点、观景点、活动、餐厅等详细地点，并 **直接插入最终线路**。

例如原线路：

```text
奥克兰
→ 罗托鲁瓦【住】
→ 陶波【住】
```

生成详细地点后可以成为：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦【住】
→ Wai-O-Tapu
→ Huka Falls
→ 陶波【住】
```

因为详细地点已经进入唯一的最终线路，所以它们同时已经属于对应 Day；不再需要另一个“每日行程生成”步骤把景点二次搬进 Day。

自动插入新地点时遵守最小影响原则：

> **AI 可以决定新地点插在哪两个已有地点之间，但不能借机改变已有地点之间的相对顺序。**

用户之后手工拖动的顺序再次成为最高事实。

---

# 12. 地点块统一

原 Step 2 和 Step 4 的地点卡片都移植到最终线路，尽量形成一种统一的“地点块”。

一个地点块主要承担：

```text
地点名称 / 摘要
当前在线路中的位置
地图定位状态
正常 / 待定 / 不去状态
是否形成住宿分界（如果适用）
编辑 / 移除
```

右侧偏好主按钮只保留：

```text
待定
不去
```

不把内部地点角色、parent、Candidate 类型等工程概念做成普通用户的管理器。

---

# 13. 定位和线路计算只认最终线路

产品不再让“候选池”“Skeleton”“每日 Stop”分别拥有自己的地图与线路真相。

定位和线路生成的输入只来自：

> **当前最终线路列表。**

只要最终线路发生变化，地图和线路就自动跟随更新，不要求用户额外执行一次“同步”动作。

会触发更新的典型变化包括：

```text
新增地点
生成主要地点
生成详细地点
编辑地点
移除地点
拖动排序
正常 ↔ 待定
正常 ↔ 不去
住宿分界变化
新增日程块
```

规则：

- 所有仍在列表里的地点都继续尝试定位并显示在地图上。
- 只有正常地点参与当前交通路线计算。
- 待定 / 不去地点仍显示地图标记，但路线跳过它们。
- 地点未定位时保留地点本身，不因为定位失败自动删除或补位。
- 真实距离、时间、geometry 等只显示 Provider 返回的事实。

---

# 14. 地图 / 时间轴与右侧唯一控制台

继续保留既有最高优先级 UX：

```text
地图 / 线路 / 日程展示
+
右侧唯一控制台
```

地图和日程本体负责：

```text
展示
选择
聚焦
```

业务操作统一在右侧控制台完成，包括：

```text
生成主要地点
生成详细地点
编辑 / 移除
待定 / 不去
住宿分界调整
AI 优化
定位修复
交通方式调整
```

同一个业务动作不要在地图 Popup、卡片、菜单和聊天区同时出现多套入口。

---

# 15. AI 的权限边界

AI 默认可以：

```text
根据旅行需求生成主要地点和初始线路结构
生成详细地点并插入现有线路
解释风险和不合理之处
提出优化建议
在用户明确授权的范围内优化线路
```

AI 默认不能：

```text
因为“更合理”而改掉用户手工排序
自动把待定 / 不去恢复成正常
静默删除用户地点
为了新景点重排已有地点
擅自改变住宿分界
擅自把一天拆成两天或把两天合并
```

用户手工修改后的 canonical 方案不需要满足 AI 的旅行启发式。

---

# 16. 增量变化原则

最终线路是唯一工作对象，因此更新应该围绕“实际变化的线路范围”进行。

原则：

> **没有受到变化影响的地点、日程和用户手工顺序保持不动。**

例如：

- 新增一个详细地点，只插入该新地点，不重做整趟旅行。
- 把一个地点设为待定，只让当前路线跳过它，不删除它、不改变其排序。
- 取消一个住宿分界，只合并由这个分界产生的相邻日程。
- 多住一晚，只新增对应日程块，不自动从前后搬景点。

需要智能重排时，由用户显式调用 AI 优化。

# 17. 一个完整的用户心智示例

```text
填写旅行需求
↓
进入最终线路
↓
生成主要住宿 / 停留地点与初始日程结构
↓
手工拖动顺序、增加一天、设置不住、待定或不去
↓
点击“生成详细地点”
↓
景点直接插入最终线路和对应日程
↓
继续手工调整
↓
需要时让 AI 优化某一天 / 某一段 / 全程
```

用户始终只是在编辑同一份最终线路，不需要理解“现在修改的是 Step 2、Step 3、Step 4 还是 Step 5”。

# 18. 产品验收原则

新的产品体验至少应满足：

```text
只有“旅行需求”和“最终线路”两个核心工作区
原 Step 2 / Step 4 不再有独立页面
原 Step 3 / Step 5 不再维护两套行程
最终线路是一份始终保序的地点列表
待定 / 不去仍留在列表和地图中，但不参与当前路线
地点卡右侧主要偏好只保留“待定 / 不去”，并保留编辑 / 移除
生成主要地点不默认每个地点住 1 晚
不存在“住几晚”这个地点属性
住宿分界直接切出 Day
两个住宿分界之间的所有有效地点属于同一天
手工不合理也允许，AI 不自动修正
生成详细地点后直接进入最终线路
自动插入新地点不改变已有地点相对顺序
最终线路一变化，定位、地图和路线自动跟随更新
地图显示正常 / 待定 / 不去全部地点，并用颜色区分
只有正常地点参与实际路线计算
右侧控制台仍是唯一业务操作入口
```

# 19. 本轮不定义的内容

本文件到此只确认 **产品逻辑和用户体验**。

本轮不决定：

```text
数据库怎么改
旧 Candidate / Skeleton / Day / Stop 如何迁移或兼容
新的数据结构具体叫什么
API 合同如何调整
Prompt 如何拆分
现有 Step 2/3/4/5 代码如何复用或删除
路由缓存 / revision / CAS 如何实现
测试和施工 Phase 如何安排
```

这些属于下一步技术设计 / 修改方案。

> **下一步应先根据本产品方案核对现有代码，形成技术修改文档；技术方案确认后再施工。**
