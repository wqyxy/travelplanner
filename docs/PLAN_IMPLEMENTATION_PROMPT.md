你现在需要根据项目 `docs/PLAN.md` 对当前项目进行修改。

项目中有三个核心文档：

* `docs/PRODUCT.md`：当前产品现状，描述**现在产品实际上是什么样**
* `docs/TECHNICAL.md`：当前技术现状，描述**现在代码和技术架构实际上是什么样**
* `docs/PLAN.md`：目标状态，描述**下一步准备把项目修改成什么样**

你的任务不是机械执行 `PLAN.md`，而是先理解现状、确认目标，再制定最小可验证的实施路径，然后逐步修改代码。

---

# 总体原则

1. `PRODUCT.md` 和 `TECHNICAL.md` 是当前状态参考。
2. `PLAN.md` 是目标方向，但不是绝对正确的实施细节。
3. 实际代码是当前实现事实的最终依据。
4. 如果文档与代码不一致：

   * 明确指出；
   * 判断这是“文档过期”还是“代码偏离设计”；
   * 不要擅自猜测用户意图。
5. 用户是最终决策者。
6. 不要为了代码结构漂亮而扩大重构范围。
7. 优先完成 PLAN 真正要求的行为变化，而不是顺手重构无关代码。
8. 尽量减少施工阶段数量，也尽量减少用户需要手动测试的次数。
9. 每一个阶段应尽可能形成一个完整、可运行、可测试的状态。
10. 不要一次性修改整个项目后才进行验证。

---

# 第一阶段：Review PLAN，不要修改代码

首先完整阅读：

* `docs/PRODUCT.md`
* `docs/TECHNICAL.md`
* `docs/PLAN.md`

然后结合当前代码进行必要检查。

这一阶段**不要修改任何业务代码**。

你的目标是确认：

* 当前产品是怎样的；
* 当前技术实现是怎样的；
* PLAN 想解决什么问题；
* PLAN 最终会把用户体验改变成什么样；
* 哪些地方属于产品行为变化；
* 哪些地方属于数据模型变化；
* 哪些地方属于前后端/API/Agent/Prompt 等技术变化；
* 是否存在迁移、兼容或旧数据处理问题；
* PLAN 中是否存在互相矛盾、定义模糊、遗漏或实现风险。

## 输出要求

不要先给我大段技术设计。

先用**人话**向我解释：

### 1. 你理解的当前状态

简单说明现在用户实际上是怎么使用这个功能的。

### 2. PLAN 修改之后会变成什么样

重点从用户体验和业务逻辑解释。

尽量使用类似：

> 现在是……
>
> 修改以后会变成……
>
> 用户操作时会……

而不是直接讲类、接口、数据库字段。

### 3. 你认为 PLAN 的核心变化

归纳成少量几个核心变化。

不要把代码改动列表当成需求总结。

### 4. 发现的问题

如果有以下情况必须指出：

* PLAN 描述不够明确；
* 两个要求之间存在冲突；
* PRODUCT / TECHNICAL / PLAN / 当前代码互相矛盾；
* 存在两种以上明显不同的产品行为；
* 需要用户做产品决策。

这种情况下直接问我。

问题要尽量少，并且只问**会实际影响产品行为或架构方向的问题**。

不要询问可以通过查看代码自行确定的问题。

### 5. 初步实施判断

简单告诉我：

* 大概需要几个实施阶段；
* 哪些是高风险部分；
* 是否涉及数据迁移；
* 是否存在可以合并施工和测试的步骤。

---

# 重要：等待需求对齐

完成上面的 Review 后停止。

**在我明确确认需求之前，不要开始修改代码。**

如果我修改、补充或纠正了 PLAN 的理解：

先更新你的理解。

必要时建议同步修改 `PLAN.md`。

需求确认完成以后，再进入下一阶段。

# 第二阶段：创建实施文档

需求确认后，在 `docs/` 下创建：

```text
docs/
├── PRODUCT.md
├── TECHNICAL.md
├── PLAN.md
├── PLAN_EXECUTION.md
└── PLAN_PROGRESS.md
```

# `PLAN_EXECUTION.md`

这个文件描述**怎么从当前状态走到 PLAN 的目标状态**。

它是施工方案，不是 PLAN 的重复描述。

至少包含：

## 1. 目标

用简短语言描述本次改造最终需要达到的状态。

## 2. 当前状态

只记录与此次改造直接相关的现状。

不要复制整个 PRODUCT.md / TECHNICAL.md。

## 3. 关键设计决定

记录已经和用户确认的决定。

例如：

* 数据模型采用什么方式；
* 旧字段如何处理；
* UI 行为如何定义；
* Agent 的职责边界；
* 哪些旧逻辑废弃；
* 哪些逻辑继续兼容。

以后施工时以这里记录的已确认决定为准。

## 4. 实施阶段

将整个改造拆成**尽可能少、但仍然安全可验证**的阶段。

不要为了形式强行拆成很多 Phase。

优先考虑：

* 一个阶段完成一整条业务闭环；
* 强相关的数据库/API/UI 改动放在一起；
* 能一次测试完成的内容尽量合并；
* 避免连续几个阶段都需要用户重复测试相同功能。

每个阶段必须包含：

### Phase N：名称

**目标**

这个阶段完成以后，系统具备什么能力。

**修改范围**

预计涉及：

* 数据模型
* 后端
* API
* 前端
* Agent
* Prompt
* 测试
* 文档

只列实际涉及的内容。

**主要修改**

说明需要做什么。

不需要在这里提前写完整代码。

**完成条件**

定义什么情况下可以认为这个阶段完成。

**自动测试**

列出应该由你自己运行的：

* unit test
* integration test
* lint
* type check
* build
* 其他必要检查

**用户测试**

描述用户真正需要手动验证的内容。

如果这个阶段没有必要让用户手测，明确写：

> 无需用户手动测试，本阶段由自动测试覆盖。

---

# 测试 Prompt

对于**需要用户手动测试的阶段**，在该 Phase 最后生成：

```markdown
## 本阶段 Codex 测试 Prompt

> ...
```

这段 Prompt 是给用户复制到**另一个本地 Codex 会话**中进行独立测试的。

测试 Prompt 不要要求测试 Agent 相信施工 Agent 的结论。

应该让测试 Agent：

1. 阅读相关代码；
2. 阅读：

   * `docs/PLAN.md`
   * `docs/PLAN_EXECUTION.md`
   * `docs/PLAN_PROGRESS.md`
3. 独立检查本阶段目标是否真的完成；
4. 运行必要测试；
5. 必要时实际启动程序或检查 UI；
6. 重点寻找：

   * 功能未完成；
   * 与 PLAN 不一致；
   * 回归问题；
   * 边界情况；
   * 数据兼容问题；
   * 状态同步问题；
7. 输出：

   * PASS / FAIL
   * 发现的问题
   * 问题严重程度
   * 是否建议进入下一阶段

测试 Prompt 应针对**本阶段实际修改内容**生成，不要使用完全一样的通用测试模板。

---

# `PLAN_PROGRESS.md`

这个文件是整个施工过程中的**实时状态记录**。

目标是：

> 即使开启一个全新的 Codex 会话，只阅读 PLAN、PLAN_EXECUTION 和 PLAN_PROGRESS，也能够知道项目目前做到哪里，以及下一步应该做什么。

推荐结构：

```markdown
# PLAN Progress

## Overall Status

当前阶段：
总体状态：
最后更新时间：

## 已确认的产品决定

- ...

## Phase 状态

### Phase 1
状态：pending / in_progress / completed / blocked

完成：
- ...

未完成：
- ...

测试：
- ...

发现的问题：
- ...

### Phase 2
状态：pending
...

## 当前已知问题

- ...

## 与原计划的偏差

- ...

## 下一步

...
```

不要把它写成开发日志流水账。

只保留对**继续施工有价值的信息**。

# 第三阶段：开始施工

完成 `PLAN_EXECUTION.md` 和初始 `PLAN_PROGRESS.md` 后，开始按照 Phase 顺序施工。

每次只推进当前 Phase。

---

# 每个 Phase 的施工流程

每个 Phase 必须遵循下面的流程。

## A. 开始前检查

先重新确认：

* 当前 Phase 的目标；
* 前一个 Phase 是否完成；
* `PLAN_PROGRESS.md` 是否存在尚未解决的 blocker；
* 当前代码是否和实施计划预期一致。

如果之前的施工导致实施方案需要调整：

可以修改 `PLAN_EXECUTION.md`。

但必须记录：

* 为什么改变；
* 原方案是什么；
* 新方案是什么。

不要悄悄偏离实施计划。

---

## B. 修改代码

完成当前 Phase 所需要的代码修改。

遵守以下原则：

* 只修改实现当前目标所必要的代码；
* 避免无关重构；
* 尽量沿用项目已有架构；
* 不为了理论上的完美破坏已有稳定逻辑；
* 对旧数据和旧行为的兼容必须符合 PLAN 中的约定。

如果实施过程中发现 PLAN 本身存在新的产品问题：

停止该产品决策相关修改。

向用户解释问题。

不要擅自决定新的产品规则。

---

## C. 自动验证

代码完成以后，你自己运行所有合理的自动验证。

例如：

* lint
* typecheck
* unit tests
* integration tests
* build
* migration test
* API test

不要把本来可以自动完成的测试交给用户。

修复你发现的问题以后再继续。

---

## D. 更新 `PLAN_PROGRESS.md`

每一个 Phase 完成代码修改和自动验证以后，立即更新：

`docs/PLAN_PROGRESS.md`

至少同步：

* Phase 当前状态；
* 已完成内容；
* 未完成内容；
* 自动测试结果；
* 已知问题；
* 与计划的偏差；
* 下一步。

**不能先连续完成多个 Phase，最后再补 Progress。**

Progress 必须跟代码状态同步。

---

# E. 输出本阶段结果

每一个需要用户验证的阶段完成后停止。

向用户输出：

## 本阶段完成

简单说明完成了什么。

## 自动测试

说明：

* 跑了哪些测试；
* 是否通过；
* 是否存在 warning。

## 需要你测试

给出一个完整的：

> **Codex 本地测试 Prompt**

用户可以直接复制到另一个 Codex 会话中。

测试 Prompt 也必须同步保存到：

`PLAN_EXECUTION.md`

对应 Phase 下。

---

# F. 等待测试结果

如果该阶段需要用户手动测试：

不要自动进入下一 Phase。

等待用户把测试结果发回来。

如果测试失败：

1. 判断问题；
2. 修复；
3. 重新运行自动测试；
4. 更新 `PLAN_PROGRESS.md`；
5. 必要时生成新的测试 Prompt。

如果测试通过：

更新：

```text
Phase N = completed
Phase N+1 = in_progress
```

然后继续下一阶段。

---

# 减少阶段和测试次数

整个实施过程必须主动优化阶段数量。

不要采用：

> 改数据库 → 测一次
> 改后端 → 测一次
> 改前端 → 测一次
> 改 Prompt → 测一次

如果这些修改共同组成一个业务功能，优先：

> 数据模型 + 后端 + 前端 + Prompt
> ↓
> 完成完整业务闭环
> ↓
> 一次集成测试

只有出现以下情况才应该拆开：

* 数据迁移风险较高；
* 基础架构需要先稳定；
* 一个阶段失败会让后续大量工作作废；
* 两个模块可以明确独立验证；
* 修改量太大，无法合理 Review；
* 必须先确认一种产品行为才能继续后面的实现。

目标不是“Phase 越少越好”，而是：

> **用最少的阶段获得足够的风险控制。**

---

# 完工阶段

所有 Phase 完成以后：

进行一次最终整体 Review。

检查：

1. `PLAN.md` 的目标是否全部实现；
2. 是否存在“代码做了，但用户体验实际上没完成”的情况；
3. PRODUCT / TECHNICAL 是否已经过时；
4. 是否存在遗留兼容代码；
5. 是否存在 TODO / 临时方案；
6. 是否存在未覆盖的边界情况；
7. 所有测试是否通过。

然后更新：

`PLAN_PROGRESS.md`

为：

```text
Overall Status: completed
```

并记录最终测试结果。

---

# 最终文档同步

项目真正完成后，判断：

* `PRODUCT.md` 是否需要更新；
* `TECHNICAL.md` 是否需要更新。

因为它们代表的是**当前实际状态**。

如果需要：

根据最终真实代码状态更新它们。

注意：

不是把 PLAN 原样复制过去。

必须描述最终实际已经实现的状态。

`PLAN.md` 保留作为本次改造目标和历史设计依据。

---

# 最重要的工作方式

始终遵循：

```text
理解现状
↓
Review PLAN
↓
用人话和用户确认
↓
确定产品决策
↓
生成实施方案
↓
拆成最少必要阶段
↓
实施一个完整阶段
↓
自动测试
↓
更新 Progress
↓
必要时用户独立测试
↓
进入下一阶段
↓
最终整体 Review
↓
同步 PRODUCT / TECHNICAL
```

不要跳过第一步的需求确认。

不要在需求还存在明显歧义时直接开始施工。
