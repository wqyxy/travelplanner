# TravelPlanner 下一步修改计划

> 状态：**下一版目标（追加 UI / 交互优化）**
> 更新日期：2026-09-06
> 当前产品现状：[`PRODUCT.md`](./PRODUCT.md)
> 当前技术现状：[`TECHNICAL.md`](./TECHNICAL.md)

本文件只记录下一版产品准备改成什么样。

---

# 1. 本轮改造目标

把当前：

```text
Step 1 旅行需求
Step 2 想去哪些地方
Step 3 路线和天数
Step 4 补充景点
Step 5 每日行程
```

收敛成两个核心工作区：

```text
规划：旅行需求
行程：最终线路
```

核心目标不是简单减少几个 Tab，而是：

> **用户以后只维护一份最终线路。地点、住宿分界、Day、地图和交通路线都围绕这一份线路工作。**

用户不再需要理解或维护 Candidate、Skeleton、Stay Block、Day Stop 等多套互相同步的产品对象。

---

# 2. 本轮不考虑现有数据兼容

当前项目中的旅行、地点、Day、Revision 等数据都属于测试数据。

因此本轮改造明确采用以下原则：

> **不考虑旧数据兼容，不做旧数据迁移，不要求旧旅行继续可读，可以从空数据重新开始。**

具体包括：

```text
不迁移旧旅行计划
不兼容旧计划 JSON 结构
不要求旧 Candidate / Skeleton / Day 数据继续工作
不要求旧 Revision 能恢复到新结构
不为了读取测试数据保留过渡字段或过渡逻辑
不为了兼容旧数据维持旧 schema
```

如果新的数据结构与旧结构冲突，可以直接：

```text
升级数据结构
清空测试数据
重新初始化数据库
重新创建测试旅行
```

但仍然必须保留真正有长期价值的数据安全能力，例如：

```text
数据结构校验
实体引用完整性
generation / 并发保护
Revision / Undo 的新结构能力
Provider 事实边界
```

这些能力只需要服务**新结构和新数据**，不需要兼容施工前的测试数据。

---

# 3. 最终线路是系统保存和用户维护的唯一线路

新的核心工作区是：

```text
最终线路
```

它是一份始终有明确顺序的地点列表：

```text
地点 A
↓
地点 B
↓
地点 C
↓
地点 D
...
```

用户以后主要围绕这一份列表完成：

```text
地点生成
地点补充
排序
住宿 / 日程分界
待定 / 不去
交通
每日线路
地图
AI 优化
```

系统也不再保存另一份可独立编辑的“用户线路”。

Day、地图和交通路线都只能根据最终线路生成或计算。

---

# 4. Step 2 和 Step 4 取消独立页面

当前 Step 2“想去哪些地方”和 Step 4“补充景点”不再保留独立工作区。

它们的地点块 UI 和生成能力迁入“最终线路”。

以后不再有：

```text
先在 Candidate 页面生成
→ 再进入另一页采用
→ 再进入另一页安排进 Day
```

而是：

```text
生成地点
→ 地点直接进入最终线路
```

---

# 5. 第一次生成：生成主要地点

原 Step 2 的首次地点生成改为最终线路中的：

```text
生成主要地点
```

这一轮 AI 主要生成整趟旅行的：

```text
主要停留地点
可能的住宿分界
建议顺序
```

生成结果直接进入最终线路。

重要规则：

> **不能因为地点被生成，就默认这个地点“住 1 晚”。**

下一版不再把：

```text
stayDays = 1 / 2 / 3
```

作为地点上的核心产品属性。

如果同一个地方实际连续停留多天，应该直接体现为多个 Day / 日程分界。

---

# 6. 地点状态只保留：正常 / 待定 / 不去

最终线路中的地点始终保留排序。

地点只有三个用户状态：

```text
正常
待定
不去
```

地点块右侧状态操作只需要：

```text
待定
不去
```

并继续保留：

```text
编辑
移除
```

不再让用户维护：

```text
必去
想去
optional
excluded
```

这样的多级偏好 UI。

---

# 7. 待定 / 不去仍然留在最终线路

待定和不去都不是“移出线路列表”。

例如：

```text
A
X（待定）
B
Y（不去）
C
```

列表顺序仍然保持：

```text
A → X → B → Y → C
```

但当前有效旅行线路跳过：

```text
A → B → C
```

以后 X / Y 恢复为正常时，直接在原位置重新生效。

“移除”才是真正删除。

---

# 8. 待定 / 不去时住宿分界暂时失效

如果：

```text
A → B【住】 → C
```

B 改成待定或不去后：

```text
当前有效线路：A → C
```

B 仍然保留在线路原位置，原来的住宿分界也仍然保存，但暂时不参与 Day 划分。

B 恢复正常后，原住宿分界自动恢复。

---

# 9. 待定 / 不去的视觉与地图

最终线路中：

```text
正常 = 正常主视觉
待定 = 深灰色 A
不去 = 深灰色 B
```

待定和不去需要明显视觉区别。

地图必须显示最终线路中的全部地点：

```text
正常
待定
不去
```

地图同样通过颜色或图标区分状态。

但是交通路线只按正常地点计算。

例如：

```text
A
X（待定）
B
Y（不去）
C
```

地图显示 5 个点，但交通路线只连接：

```text
A → B → C
```

---

# 10. 所有日程都来自同一条线性线路

核心规则：

> **先有最终线路顺序，住宿分界只负责把这条线路切成 Day。**

例如：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦【住宿分界】
→ Wai-O-Tapu
→ 陶波
→ 惠灵顿【住宿分界】
```

自动得到：

```text
Day 1：奥克兰 → Hobbiton → 罗托鲁瓦
Day 2：罗托鲁瓦 → Wai-O-Tapu → 陶波 → 惠灵顿
```

两个连续住宿分界之间的全部正常地点都属于同一个 Day。

不再维护“这个地点属于哪一天”的第二套关系。

---

# 11. 手工结果优先，不做自动合理化

即使用户手工形成：

```text
一天太长
路线明显绕路
地点很多
交通不现实
```

系统也不能自动修改。

产品可以提醒：

```text
这一天可能过长
当前路线可能很绕
交通时间可能较高
```

但只能提醒。

只有用户明确调用：

```text
优化这一天
优化这一段
优化全程
```

AI 才获得对应范围内重排已有线路的权限。

---

# 12. 住宿不是地点类型，而是 Day 分界

“住”以后不表示某种 Place 类型，也不维护一个 `stayDays` 数字。

住宿只表达：

> **这里是一日结束的位置。**

需要支持：

```text
住
多一晚
不住
```

---

# 13. “不住”的确定行为

如果当前：

```text
Day 1：A → B【住】
Day 2：B → C → D【住】
```

用户把 B 改成“不住”，系统只做机械变化：

```text
Day 1：A → B → C → D【住】
```

也就是说：

> **从上一个住宿点之后，到下一个住宿点为止，所有正常地点属于同一天。**

系统不能因为结果不合理而帮用户重新拆分。

必须严格区分：

```text
不住 = 仍然去这个地方，只取消日程分界
不去 = 地点暂时不参与实际路线，但保留在线路排序和地图
```

---

# 14. “多一晚”的确定行为

如果当前：

```text
Day 3：A → 陶波
Day 4：陶波 → B
```

用户在陶波“多一晚”，系统直接增加一个 Day：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

新增 Day 可以暂时没有详细地点。

后续用户可以：

```text
自己拖地点进去
生成详细地点
让 AI 优化这一天
```

但“多一晚”本身不能自动搬动前后已有景点。

技术上允许最终线路中出现两个引用同一 Place 的独立线路节点。

---

# 15. 不再保留“住几晚”属性

下一版产品不再需要：

```text
陶波 · 住 2 晚
```

这样的地点属性。

如果陶波连续停留两晚，产品实际状态就是存在两个连续日程块。

例如：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

后续 Day 4 可以变成：

```text
陶波 → Huka Falls → Tongariro → 陶波
```

“连续住 2 晚”如果需要展示，只能根据实际 Day 推导成摘要，不能成为另一份需要同步的数据。

---

# 16. 第一日和最后一日

第一天：

> 从旅行起点开始，到第一个有效住宿分界结束。

旅行起点可以是：

```text
机场
城市
酒店
租车点
任意地点
```

最后一天允许没有住宿。

例如：

```text
皇后镇【上一晚住宿】
→ 箭镇
→ 皇后镇机场【行程结束】
```

这是合法最后一天。

不需要为了数据结构强行制造一个住宿终点。

---

# 17. Day 编号自动生成

Day 1 / Day 2 / Day 3 不作为用户手工维护的永久编号。

住宿分界变化后，Day 编号自动连续重新计算。

例如删除一个住宿分界后：

```text
原 Day 1 + Day 2 合并
原 Day 3 自动显示为新的 Day 2
```

底层可以有稳定 Day ID，但用户看到的 Day 编号必须始终根据当前最终线路得到。

---

# 18. 交通方式属于“到达当前节点”

每个线路节点保存：

> **从上一个当前有效地点到达当前地点时使用什么交通方式。**

例如：

```text
A —自驾→ X —步行→ B
```

如果 X 改成待定或不去：

```text
A —步行→ B
```

B 自己保存的交通方式继续用于新的上一有效地点 A。

X 恢复正常以后：

```text
A —自驾→ X —步行→ B
```

原设置一起恢复。

---

# 19. 第二次生成：生成详细地点

原 Step 4 的能力迁入最终线路。

主要线路存在以后，用户直接点击：

```text
生成详细地点
```

AI 可以生成：

```text
景点
观景点
活动
餐厅
其他详细地点
```

并直接插入最终线路。

例如：

```text
奥克兰
→ 罗托鲁瓦【住】
→ 陶波【住】
```

生成后：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦【住】
→ Wai-O-Tapu
→ Huka Falls
→ 陶波【住】
```

地点一旦进入最终线路，就已经属于对应 Day。

不再需要第二次“把 Candidate 安排成 Stop”。

---

# 20. AI 自动插入详细地点的权限边界

新增 X 时，AI 可以决定：

> **X 插在哪两个已有地点之间。**

但不能借机改变已有地点的相对顺序。

例如原来：

```text
A → B → C → D
```

新增 X 后允许：

```text
X → A → B → C → D
A → X → B → C → D
A → B → X → C → D
A → B → C → X → D
A → B → C → D → X
```

但不能自动变成：

```text
A → C → X → B → D
```

除非用户明确授权 AI 优化。

新增详细地点时还不能擅自：

```text
删除已有地点
改变待定 / 不去状态
改变住宿分界
移动已有地点到其他 Day
```

---

# 21. 详细地点生成支持局部范围

“生成详细地点”不应该只能整趟旅行执行一次。

后续应支持围绕：

```text
某个 Day
某一段线路
某个住宿点附近
```

局部生成。

未选中的其他线路保持不变。

---

# 22. 定位、Day 和路线只根据最终线路更新

下一版必须把：

```text
地图定位
路线计算
Day 划分
交通线路展示
```

统一改成围绕最终线路工作。

只要最终线路变化，就自动更新对应结果。

典型变化包括：

```text
新增地点
生成主要地点
生成详细地点
编辑地点
移除地点
拖动排序
正常 ↔ 待定
正常 ↔ 不去
住宿分界变化
多一晚
交通方式变化
```

用户不再需要理解：

```text
上游过期
Macro dirty
Step 5 需更新
Candidate 还没进 Day
```

对用户来说只需要：

> **最终线路变了，地图、Day 和路线自动跟着变。**

---

# 23. 地图 Provider 边界继续保留

虽然线路结构会重做，但当前已经正确的 Provider 边界必须保留：

```text
地点可以先保存、后定位
定位失败不自动删除地点
不自动补位
正常 / 待定 / 不去都可以定位
地图只展示真实坐标
距离 / 时长 / geometry 只能来自 Provider
```

待定 / 不去虽然不参与交通路线，但仍然需要地图定位，因为地图仍要显示它们。

---

# 24. 右侧是唯一业务操作入口

现有“地图主要负责展示和选择、业务操作集中在右侧”的设计继续保留。

最终线路中的主要业务动作都集中在右侧：

```text
生成主要地点
生成详细地点
待定 / 不去
编辑 / 移除
住 / 不住 / 多一晚
交通方式
定位修复
AI 优化
```

地图 Popup 不新增第二套删除、状态、生成、住宿或优化入口。

---

# 25. 当前技术结构需要重点改造的部分

基于 [`TECHNICAL.md`](./TECHNICAL.md) 的现状，本轮至少涉及：

```text
WorkflowStep 五步导航
Candidate 作为独立候选池的产品职责
PlanningRole 在产品流程中的强分层
SkeletonStayDraft / stayDays
Skeleton → Day 展开逻辑
Step 4 Candidate → Step 5 DayStop 的二次安排
Macro / Detail 两层路线依赖
itineraryUpdateState 的五步同步语义
Candidate / Day / Stop 多层编辑入口
现有 destination / interest / itinerary Action 分工
相关 Prompt
相关测试
```

这些都需要围绕“用户只维护最终线路”重新设计。

因为现有数据都是测试数据，这一轮技术设计不需要增加旧数据转换层、兼容读取层或旧结构双写层。

---

# 26. 当前能力中应尽量保留的部分

重构不是全部推翻。

当前已有这些能力应尽量复用：

```text
Place 实体
PlaceResolution / Provider 事实边界
详细地点的交通 / 时间 / 备注表达能力
Route legs
Scope / generation / CAS
Proposal / Revision / Undo
Planning Advisory
用户手工优先原则
局部 AI Scope
WebSocket 自动刷新
地图选择 / 聚焦
```

重点是简化产品和数据关系，不是丢掉已经稳定的安全与基础设施能力。

其中 Revision / Undo 只需要覆盖新结构产生的新数据，不需要恢复施工前的测试 Revision。

---

# 27. 技术设计时必须回答的问题

正式施工时，需要基于当前代码确定：

1. 最终线路具体使用什么数据结构表达。
2. Candidate 是否还有必要作为内部 AI 研究对象；如果没有必要可以直接删除其新流程职责。
3. 同一个 Place 在线路中多次出现时，如何表示多个独立线路节点。
4. 住宿分界如何稳定表达，而不再依赖地点级 `stayDays`。
5. Day 是完全由最终线路生成，还是保留稳定 ID 但内容由最终线路生成。
6. 待定 / 不去状态放在线路节点的哪一层，如何保证排序始终保留。
7. Macro Route 是否彻底取消，还是降为最终线路路线结果的一种展示方式。
8. 现有 destination / interest / itinerary Action 如何收敛。
9. 哪些 Prompt 可以复用，哪些必须重写。
10. 如何做到最终线路变化后定位 / Day / Route 自动局部刷新。
11. Revision / Undo 如何覆盖拖动、状态变化、住宿分界变化、多一晚等新操作。
12. 新结构上线时如何清理旧测试数据并初始化新的空数据环境。

明确不再需要回答：

```text
旧旅行如何迁移
旧计划 JSON 如何兼容
旧 Revision 如何恢复
新旧结构如何双写
```

---

# 28. 本轮验收目标

完成本计划后，用户应该感受到：

```text
我先填写旅行需求
→ 进入最终线路
→ AI 先生成主要停留 / 住宿节点
→ 我直接在线路上调整
→ 我可以生成详细地点
→ 详细地点直接进入对应日程
→ 我继续拖动、待定、不去、住 / 不住 / 多一晚
→ 地图和路线自动跟着变
→ 只有我明确要求时 AI 才优化已有顺序
```

用户不再需要理解：

```text
Step 2 候选
Step 3 Skeleton
Step 4 Detail Interest
Step 5 Day Stop
Macro / Detail 同步
stayDays
旧数据迁移
旧结构兼容
```

---

# 29. 数据重置验收原则

因为所有现有数据都是测试数据，本轮允许用以下方式完成新结构切换：

```text
删除旧测试旅行
清空旧数据库
重建数据库 schema
重新创建旅行
重新生成地点和日程
```

因此验收重点是：

```text
新建旅行是否正确
新结构是否简单一致
最终线路是否唯一
人工操作是否稳定
AI 权限是否正确
Day / 地图 / Route 是否自动跟随
Revision / Undo 是否对新数据工作
Provider 事实边界是否保持
```

不要把时间投入在旧测试数据迁移成功率上。

---

# 30. 下一步施工原则

后续实施方案必须遵守：

1. 不再为了兼容旧测试数据增加代码。
2. 如果已经写了只为旧数据兼容服务的过渡代码，应评估删除，而不是继续扩展。
3. 可以直接设计最简单的新旅行计划结构。
4. 可以直接升级或重建测试数据库结构。
5. Day / Route 只围绕最终线路工作，不再维持旧五步的双向同步。
6. Revision / Undo 从新结构开始重新保证。
7. 每个 Phase 按 `PLAN_IMPLEMENTATION_PROMPT.md` 要求交给用户本地 Codex 测试。
8. 测试只验证指定 Git Branch + HEAD。

下一步应根据本 PLAN 重新检查 `PLAN_EXECUTION.md` 和 `PLAN_PROGRESS.md`：

> **删除旧数据兼容、旧 Revision 恢复、新旧结构双写等已经不再需要的施工内容，然后继续实现更简单的新结构。**

---

# 31. 追加目标：最终线路 UI 必须像一条线，而不是 Day 配置表单

前 1–30 节的 finalRoute、派生 Day、Route、AI 权限和 Provider 边界继续成立。

本次 UI 追加改造不重新设计 finalRoute 数据模型，只固定最终线路的视觉语法：

```text
地点 = 统一地点卡
交通 = 两个当前有效地点之间的连接条
住宿 / Day = 地点之间的“第 N 晚”分隔线
编辑 = 显式按钮打开独立编辑抽屉
地图 = 与地点列表联动，但不抢夺编辑入口
```

核心原则：

> **地点永远只是地点；Day 是这条线上的时间分界，不是另一层包住地点的用户线路。**

禁止再把 Day 做成包住一组地点的大卡片 / Header。

# 32. 最终线路的视觉层级固定为：地点 → 交通 → 夜晚分隔

最终线路右侧的核心结构：

```text
奥克兰

    🚗 自驾 · 72 km · 58 分

Hobbiton

    🚗 自驾 · 105 km · 1小时20分

罗托鲁瓦   [住]

──────── 第 1 晚 ────────

    🚗 自驾 · 28 km · 35 分

Wai-O-Tapu
```

必须坚持：

```text
每一个 finalRoute node 都是同一种地点卡
交通条只是有效地点之间的连接
normal + endsDay 后显示第 N 晚分隔线
```

不得出现：

```text
Day 2 前往皇后镇
Day 3 陶波周边
当天终点：xxx
```

这类文字取代地点身份。

地点主标题只能来自 Place 名称展示逻辑；Place 缺失时只能使用“未命名地点”等中性 fallback，不能使用 `activity`、派生 `Day.title` 或“前往 xxx”作为地点名。

# 33. 两个地点之间使用非卡片式有效交通条

交通条放在两个**当前有效地点**之间：

```text
        🚗 自驾 · 72 km · 58 分
        ─────────────────
```

默认展示：

```text
交通方式
Provider 返回的距离
Provider 返回的时间
```

规则：

1. 交通方式仍保存在“到达当前节点”的 `transportFromPrevious` 上。
2. 点击真实交通条，只修改这一段交通方式。
3. 距离、时长、geometry 只能来自 Route Provider。
4. Route 未计算时显示“路线待计算 / 更新中”，不能编造数字。
5. Route dirty 时不能把旧数字当当前事实。
6. Provider 失败时地点和交通方式仍保留，显示路线不可用状态。
7. 交通条不是地点卡。

交通表达当前**有效线路**，不是 DOM 上下两个视觉相邻地点。

例如：

```text
A
X【待定】
B
```

当前有效交通必须是：

```text
A → B
```

实现必须从 active finalRoute + 派生 Day + `routeStates.route.legs` 构建有效交通 ViewModel，正确处理 Day Anchor / Stop ID 差异。

同 Place 连续住宿形成的 synthetic same-place hop 不是一段真实交通，不能显示“交通待定”并诱导用户修改不存在的交通事实。

# 34. 地点 Hover / Click / Edit 是三个不同动作

## Hover 地点

```text
地点卡轻微高亮
对应 Marker 高亮
```

绝对不能：

```text
移动地图
改变中心
改变 zoom
打开编辑
写入计划
```

## Click 地点

```text
地图 flyTo 当前地点
Marker 保持选中
不打开编辑抽屉
```

## Click 编辑

```text
不触发 flyTo
打开当前地点编辑抽屉
```

固定语义：

```text
Hover 地点 = 只高亮
Click 地点 = 地图飞过去
Click 编辑 = 打开地点编辑抽屉
Click 交通条 = 编辑真实有效交通方式
Click 住 / 不住 / 多一晚 = 修改 Day 分界
```

按钮必须避免把点击误传成地点主体的地图聚焦动作。

# 35. UI 状态拆成 hover / map selection / editing 三层

前端必须明确区分：

```text
hoveredNodeId
地图当前选中 / 聚焦 nodeId
editingNodeId
显式 map focus request
map-pick 上下文
```

规则：

- Hover 只影响高亮。
- 地点 Click 才创建显式地图 focus 请求。
- 编辑只改变 editing 状态。
- Marker Click 可以改变地图选择，但不能自动打开业务编辑。
- 编辑抽屉关闭不要求清空地图选中。
- 切换旅行或离开最终线路时清理临时 editing / hover / map-pick 状态。

# 36. 地点详细信息使用独立编辑抽屉

取消地点下面 inline 展开大表单。

桌面端点击“编辑”后，抽屉从最终线路列表左侧向地图方向覆盖地图一部分，不改变地点列表宽度，也不把后续地点向下推。

抽屉包含：

### 行程安排

```text
活动说明
时段
开始时间
结束时间
停留时间
备注
```

### 地点信息

```text
中文名称
英文名称
当地名称
地点类型
```

### 地图定位

```text
当前定位状态 / 地址
重新识别
地图选点
Google Maps 链接
```

### 危险操作

```text
从当前线路移除
```

交通方式不放进地点编辑抽屉。

交互：

```text
编辑 A → 打开 A
编辑 B → 直接切换 B
再点当前编辑 → 收回
关闭按钮 / Esc → 收回
切换旅行 / 工作区 → 收回
删除当前 node 成功 → 收回
```

窄屏改成覆盖式 Sheet / 全宽编辑层，但不能回退成 inline。

# 37. 地图选点是编辑抽屉中的专门模式

用户点击“地图选点”以后：

```text
保存当前 editing 上下文
→ 抽屉临时退出
→ 地图显示明确选点提示
→ 用户选点
→ 保存或取消
→ 恢复同一个地点编辑上下文
```

选点期间不能让抽屉遮住主要地图操作区。

# 38. 住 / 不住 / 多一晚位于地点卡主界面

普通地点直接提供：

```text
+ 住
```

住宿分界地点显示：

```text
住 ▾
```

至少包含：

```text
多一晚
不住
```

待定 / 不去地点可以保存 `endsDay`，但只显示“暂不生效”，不能渲染当前有效的夜晚分隔线。

# 39. Day 的视觉表达只有“第 N 晚”分隔线

线路主体不再显示包住地点的 Day 大卡片 / Day Header。

当：

```text
node.status === normal
node.endsDay === true
```

该地点之后显示：

```text
──────── 第 N 晚 ────────
```

第一条分隔线之前自然是 Day 1；第 1 晚和第 2 晚之间自然是 Day 2，以此类推。

Day 编号、日期、Route scope 等仍然可以由派生 `plan.days` 使用，但不能反过来创建第二套可编辑线路层级。

“多一晚”继续通过同 Place 的独立 route node 表达，例如：

```text
陶波【住】
──────── 第 3 晚 ────────
陶波【住】
──────── 第 4 晚 ────────
下一地点
```

两个“陶波”仍然都是普通地点卡，不允许一个变成“Day 4 陶波”之类特殊卡片。

# 41. 添加地点的插入位置必须显式

新增地点时必须明确告诉用户会插在哪里，例如：

```text

```

或：

```text
+ 添加到线路末尾
```

不能让用户不可见的 selection 暗中决定插入位置。

editing / map selection 也不能偷偷成为添加位置来源，除非当前文案明确显示这一行为。

# 42. 排序：把手启动，整张地点卡跟随，松手自动重排

桌面端只有拖动把手可以启动排序：

```text
⠿  地点名称
```

但拖动开始以后，被拖动的视觉对象必须是**整张地点卡**。

完整交互：

```text
按住把手
→ 整张地点卡作为 drag image 跟随鼠标
→ 经过目标地点上半 / 下半区域
→ 显示清楚的 before / after 插入位置线
→ 松手
→ 自动提交 move_final_route_node
→ finalRoute 顺序立即更新
→ 第 N 晚分隔、Day、有效交通、Route 自动重新派生
```

禁止：

```text
只有小把手图标单独跟着鼠标
整张卡任意位置都可误触拖动
拖完后还要求用户点“保存顺序”
桌面长期依赖上移 / 下移作为主入口
```

可以复用旧 `ItineraryPanelV2` 的 native drag / dataTransfer 思路。

目标索引必须符合当前 `moveFinalRouteNodeV3` 的“先移除原节点，再按 targetIndex 插入”语义，向上、向下、首位、末位和 no-op 都要测试。

移动端如果 native drag 体验不足，可以保留独立 fallback，但不能改变 finalRoute 唯一排序语义。

# 43. AI 操作是辅助，不成为线路层级

AI 继续是辅助工具。

因为线路主体没有 Day Header，Day 级动作现阶段放到统一 AI 辅助区，通过派生 Day scope 选择：

```text
第 N 天
→ 补充详细地点
→ 完善这一天
→ 优化这一天
```

全程 / 区段动作继续包括：

```text
生成详细地点
补充这一段
优化这一段
优化全程
```

Phase 5 再进一步折叠 AI 菜单、Proposal 等界面。

无论 UI 如何调整，都不能改变：普通生成只新增地点，只有明确“优化”才可提出已有地点重排。

当前浏览器 `window.confirm` 与产品整体交互不一致。

在 Revision / Undo 能力允许时，地点移除优先改成：


删除永远只删除当前这一次 route node，不得顺带删除同 Place 的其他线路节点。

# 47. 本次追加改造的技术原则

1. 默认只改前端展示与 UI 临时状态，不重构 finalRoute / Day / Route 服务端核心模型。
2. 地点主标题只来自 Place 名称展示逻辑，不使用 activity / Day title 作为 fallback。
3. `endsDay` 只负责派生 Day，并在 UI 中表现为当前有效的“第 N 晚”分隔线。
4. 交通距离和时长复用 `routeStates.route.legs`，禁止前端自行估算真实路线事实。
5. 有效交通必须基于 active finalRoute + 派生 Day / Anchor / Stop + RouteLeg，不能依赖 DOM 相邻。
6. hover / map selection / editing 是前端临时状态，不写旅行文档和 Revision。
7. 用户修改状态、住宿、排序、交通、地点资料继续走现有 command / API / generation 保护。
8. 排序继续使用 `move_final_route_node`；UI before / after 槽位需要转换为服务端 post-removal targetIndex。
9. 地图不是第二业务 mutation 入口；Marker Click 只能选择 / 聚焦。
10. 多一晚继续使用同 Place 独立 route node，不新增 stayDays / StayBlock。
11. 优先用可测试纯函数承载有效交通和拖动索引推导，减少 JSX 临时业务逻辑。
12. 每个施工 Phase 遵守 `PLAN_IMPLEMENTATION_PROMPT.md`：施工 Agent 不运行测试；冻结 Branch + HEAD 后交给用户本地 Codex 验证。
