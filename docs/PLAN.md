# TravelPlanner 下一步修改计划

> 状态：**下一版目标（追加 UI / 交互优化）**  
> 更新日期：2026-09-06  
> 当前产品现状：[`PRODUCT.md`](./PRODUCT.md)  
> 当前技术现状：[`TECHNICAL.md`](./TECHNICAL.md)

本文件只记录下一版产品准备改成什么样。

---

# 1. 本轮改造目标

把当前：

```text
Step 1 旅行需求
Step 2 想去哪些地方
Step 3 路线和天数
Step 4 补充景点
Step 5 每日行程
```

收敛成两个核心工作区：

```text
规划：旅行需求
行程：最终线路
```

核心目标不是简单减少几个 Tab，而是：

> **用户以后只维护一份最终线路。地点、住宿分界、Day、地图和交通路线都围绕这一份线路工作。**

用户不再需要理解或维护 Candidate、Skeleton、Stay Block、Day Stop 等多套互相同步的产品对象。

---

# 2. 本轮不考虑现有数据兼容

当前项目中的旅行、地点、Day、Revision 等数据都属于测试数据。

因此本轮改造明确采用以下原则：

> **不考虑旧数据兼容，不做旧数据迁移，不要求旧旅行继续可读，可以从空数据重新开始。**

具体包括：

```text
不迁移旧旅行计划
不兼容旧计划 JSON 结构
不要求旧 Candidate / Skeleton / Day 数据继续工作
不要求旧 Revision 能恢复到新结构
不为了读取测试数据保留过渡字段或过渡逻辑
不为了兼容旧数据维持旧 schema
```

如果新的数据结构与旧结构冲突，可以直接：

```text
升级数据结构
清空测试数据
重新初始化数据库
重新创建测试旅行
```

但仍然必须保留真正有长期价值的数据安全能力，例如：

```text
数据结构校验
实体引用完整性
generation / 并发保护
Revision / Undo 的新结构能力
Provider 事实边界
```

这些能力只需要服务**新结构和新数据**，不需要兼容施工前的测试数据。

---

# 3. 最终线路是系统保存和用户维护的唯一线路

新的核心工作区是：

```text
最终线路
```

它是一份始终有明确顺序的地点列表：

```text
地点 A
↓
地点 B
↓
地点 C
↓
地点 D
...
```

用户以后主要围绕这一份列表完成：

```text
地点生成
地点补充
排序
住宿 / 日程分界
待定 / 不去
交通
每日线路
地图
AI 优化
```

系统也不再保存另一份可独立编辑的“用户线路”。

Day、地图和交通路线都只能根据最终线路生成或计算。

---

# 4. Step 2 和 Step 4 取消独立页面

当前 Step 2“想去哪些地方”和 Step 4“补充景点”不再保留独立工作区。

它们的地点块 UI 和生成能力迁入“最终线路”。

以后不再有：

```text
先在 Candidate 页面生成
→ 再进入另一页采用
→ 再进入另一页安排进 Day
```

而是：

```text
生成地点
→ 地点直接进入最终线路
```

---

# 5. 第一次生成：生成主要地点

原 Step 2 的首次地点生成改为最终线路中的：

```text
生成主要地点
```

这一轮 AI 主要生成整趟旅行的：

```text
主要停留地点
可能的住宿分界
建议顺序
```

生成结果直接进入最终线路。

重要规则：

> **不能因为地点被生成，就默认这个地点“住 1 晚”。**

下一版不再把：

```text
stayDays = 1 / 2 / 3
```

作为地点上的核心产品属性。

如果同一个地方实际连续停留多天，应该直接体现为多个 Day / 日程分界。

---

# 6. 地点状态只保留：正常 / 待定 / 不去

最终线路中的地点始终保留排序。

地点只有三个用户状态：

```text
正常
待定
不去
```

地点块右侧状态操作只需要：

```text
待定
不去
```

并继续保留：

```text
编辑
移除
```

不再让用户维护：

```text
必去
想去
optional
excluded
```

这样的多级偏好 UI。

---

# 7. 待定 / 不去仍然留在最终线路

待定和不去都不是“移出线路列表”。

例如：

```text
A
X（待定）
B
Y（不去）
C
```

列表顺序仍然保持：

```text
A → X → B → Y → C
```

但当前有效旅行线路跳过：

```text
A → B → C
```

以后 X / Y 恢复为正常时，直接在原位置重新生效。

“移除”才是真正删除。

---

# 8. 待定 / 不去时住宿分界暂时失效

如果：

```text
A → B【住】 → C
```

B 改成待定或不去后：

```text
当前有效线路：A → C
```

B 仍然保留在线路原位置，原来的住宿分界也仍然保存，但暂时不参与 Day 划分。

B 恢复正常后，原住宿分界自动恢复。

---

# 9. 待定 / 不去的视觉与地图

最终线路中：

```text
正常 = 正常主视觉
待定 = 深灰色 A
不去 = 深灰色 B
```

待定和不去需要明显视觉区别。

地图必须显示最终线路中的全部地点：

```text
正常
待定
不去
```

地图同样通过颜色或图标区分状态。

但是交通路线只按正常地点计算。

例如：

```text
A
X（待定）
B
Y（不去）
C
```

地图显示 5 个点，但交通路线只连接：

```text
A → B → C
```

---

# 10. 所有日程都来自同一条线性线路

核心规则：

> **先有最终线路顺序，住宿分界只负责把这条线路切成 Day。**

例如：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦【住宿分界】
→ Wai-O-Tapu
→ 陶波
→ 惠灵顿【住宿分界】
```

自动得到：

```text
Day 1：奥克兰 → Hobbiton → 罗托鲁瓦
Day 2：罗托鲁瓦 → Wai-O-Tapu → 陶波 → 惠灵顿
```

两个连续住宿分界之间的全部正常地点都属于同一个 Day。

不再维护“这个地点属于哪一天”的第二套关系。

---

# 11. 手工结果优先，不做自动合理化

即使用户手工形成：

```text
一天太长
路线明显绕路
地点很多
交通不现实
```

系统也不能自动修改。

产品可以提醒：

```text
这一天可能过长
当前路线可能很绕
交通时间可能较高
```

但只能提醒。

只有用户明确调用：

```text
优化这一天
优化这一段
优化全程
```

AI 才获得对应范围内重排已有线路的权限。

---

# 12. 住宿不是地点类型，而是 Day 分界

“住”以后不表示某种 Place 类型，也不维护一个 `stayDays` 数字。

住宿只表达：

> **这里是一日结束的位置。**

需要支持：

```text
住
多一晚
不住
```

---

# 13. “不住”的确定行为

如果当前：

```text
Day 1：A → B【住】
Day 2：B → C → D【住】
```

用户把 B 改成“不住”，系统只做机械变化：

```text
Day 1：A → B → C → D【住】
```

也就是说：

> **从上一个住宿点之后，到下一个住宿点为止，所有正常地点属于同一天。**

系统不能因为结果不合理而帮用户重新拆分。

必须严格区分：

```text
不住 = 仍然去这个地方，只取消日程分界
不去 = 地点暂时不参与实际路线，但保留在线路排序和地图
```

---

# 14. “多一晚”的确定行为

如果当前：

```text
Day 3：A → 陶波
Day 4：陶波 → B
```

用户在陶波“多一晚”，系统直接增加一个 Day：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

新增 Day 可以暂时没有详细地点。

后续用户可以：

```text
自己拖地点进去
生成详细地点
让 AI 优化这一天
```

但“多一晚”本身不能自动搬动前后已有景点。

技术上允许最终线路中出现两个引用同一 Place 的独立线路节点。

---

# 15. 不再保留“住几晚”属性

下一版产品不再需要：

```text
陶波 · 住 2 晚
```

这样的地点属性。

如果陶波连续停留两晚，产品实际状态就是存在两个连续日程块。

例如：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

后续 Day 4 可以变成：

```text
陶波 → Huka Falls → Tongariro → 陶波
```

“连续住 2 晚”如果需要展示，只能根据实际 Day 推导成摘要，不能成为另一份需要同步的数据。

---

# 16. 第一日和最后一日

第一天：

> 从旅行起点开始，到第一个有效住宿分界结束。

旅行起点可以是：

```text
机场
城市
酒店
租车点
任意地点
```

最后一天允许没有住宿。

例如：

```text
皇后镇【上一晚住宿】
→ 箭镇
→ 皇后镇机场【行程结束】
```

这是合法最后一天。

不需要为了数据结构强行制造一个住宿终点。

---

# 17. Day 编号自动生成

Day 1 / Day 2 / Day 3 不作为用户手工维护的永久编号。

住宿分界变化后，Day 编号自动连续重新计算。

例如删除一个住宿分界后：

```text
原 Day 1 + Day 2 合并
原 Day 3 自动显示为新的 Day 2
```

底层可以有稳定 Day ID，但用户看到的 Day 编号必须始终根据当前最终线路得到。

---

# 18. 交通方式属于“到达当前节点”

每个线路节点保存：

> **从上一个当前有效地点到达当前地点时使用什么交通方式。**

例如：

```text
A —自驾→ X —步行→ B
```

如果 X 改成待定或不去：

```text
A —步行→ B
```

B 自己保存的交通方式继续用于新的上一有效地点 A。

X 恢复正常以后：

```text
A —自驾→ X —步行→ B
```

原设置一起恢复。

---

# 19. 第二次生成：生成详细地点

原 Step 4 的能力迁入最终线路。

主要线路存在以后，用户直接点击：

```text
生成详细地点
```

AI 可以生成：

```text
景点
观景点
活动
餐厅
其他详细地点
```

并直接插入最终线路。

例如：

```text
奥克兰
→ 罗托鲁瓦【住】
→ 陶波【住】
```

生成后：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦【住】
→ Wai-O-Tapu
→ Huka Falls
→ 陶波【住】
```

地点一旦进入最终线路，就已经属于对应 Day。

不再需要第二次“把 Candidate 安排成 Stop”。

---

# 20. AI 自动插入详细地点的权限边界

新增 X 时，AI 可以决定：

> **X 插在哪两个已有地点之间。**

但不能借机改变已有地点的相对顺序。

例如原来：

```text
A → B → C → D
```

新增 X 后允许：

```text
X → A → B → C → D
A → X → B → C → D
A → B → X → C → D
A → B → C → X → D
A → B → C → D → X
```

但不能自动变成：

```text
A → C → X → B → D
```

除非用户明确授权 AI 优化。

新增详细地点时还不能擅自：

```text
删除已有地点
改变待定 / 不去状态
改变住宿分界
移动已有地点到其他 Day
```

---

# 21. 详细地点生成支持局部范围

“生成详细地点”不应该只能整趟旅行执行一次。

后续应支持围绕：

```text
某个 Day
某一段线路
某个住宿点附近
```

局部生成。

未选中的其他线路保持不变。

---

# 22. 定位、Day 和路线只根据最终线路更新

下一版必须把：

```text
地图定位
路线计算
Day 划分
交通线路展示
```

统一改成围绕最终线路工作。

只要最终线路变化，就自动更新对应结果。

典型变化包括：

```text
新增地点
生成主要地点
生成详细地点
编辑地点
移除地点
拖动排序
正常 ↔ 待定
正常 ↔ 不去
住宿分界变化
多一晚
交通方式变化
```

用户不再需要理解：

```text
上游过期
Macro dirty
Step 5 需更新
Candidate 还没进 Day
```

对用户来说只需要：

> **最终线路变了，地图、Day 和路线自动跟着变。**

---

# 23. 地图 Provider 边界继续保留

虽然线路结构会重做，但当前已经正确的 Provider 边界必须保留：

```text
地点可以先保存、后定位
定位失败不自动删除地点
不自动补位
正常 / 待定 / 不去都可以定位
地图只展示真实坐标
距离 / 时长 / geometry 只能来自 Provider
```

待定 / 不去虽然不参与交通路线，但仍然需要地图定位，因为地图仍要显示它们。

---

# 24. 右侧是唯一业务操作入口

现有“地图主要负责展示和选择、业务操作集中在右侧”的设计继续保留。

最终线路中的主要业务动作都集中在右侧：

```text
生成主要地点
生成详细地点
待定 / 不去
编辑 / 移除
住 / 不住 / 多一晚
交通方式
定位修复
AI 优化
```

地图 Popup 不新增第二套删除、状态、生成、住宿或优化入口。

---

# 25. 当前技术结构需要重点改造的部分

基于 [`TECHNICAL.md`](./TECHNICAL.md) 的现状，本轮至少涉及：

```text
WorkflowStep 五步导航
Candidate 作为独立候选池的产品职责
PlanningRole 在产品流程中的强分层
SkeletonStayDraft / stayDays
Skeleton → Day 展开逻辑
Step 4 Candidate → Step 5 DayStop 的二次安排
Macro / Detail 两层路线依赖
itineraryUpdateState 的五步同步语义
Candidate / Day / Stop 多层编辑入口
现有 destination / interest / itinerary Action 分工
相关 Prompt
相关测试
```

这些都需要围绕“用户只维护最终线路”重新设计。

因为现有数据都是测试数据，这一轮技术设计不需要增加旧数据转换层、兼容读取层或旧结构双写层。

---

# 26. 当前能力中应尽量保留的部分

重构不是全部推翻。

当前已有这些能力应尽量复用：

```text
Place 实体
PlaceResolution / Provider 事实边界
详细地点的交通 / 时间 / 备注表达能力
Route legs
Scope / generation / CAS
Proposal / Revision / Undo
Planning Advisory
用户手工优先原则
局部 AI Scope
WebSocket 自动刷新
地图选择 / 聚焦
```

重点是简化产品和数据关系，不是丢掉已经稳定的安全与基础设施能力。

其中 Revision / Undo 只需要覆盖新结构产生的新数据，不需要恢复施工前的测试 Revision。

---

# 27. 技术设计时必须回答的问题

正式施工时，需要基于当前代码确定：

1. 最终线路具体使用什么数据结构表达。
2. Candidate 是否还有必要作为内部 AI 研究对象；如果没有必要可以直接删除其新流程职责。
3. 同一个 Place 在线路中多次出现时，如何表示多个独立线路节点。
4. 住宿分界如何稳定表达，而不再依赖地点级 `stayDays`。
5. Day 是完全由最终线路生成，还是保留稳定 ID 但内容由最终线路生成。
6. 待定 / 不去状态放在线路节点的哪一层，如何保证排序始终保留。
7. Macro Route 是否彻底取消，还是降为最终线路路线结果的一种展示方式。
8. 现有 destination / interest / itinerary Action 如何收敛。
9. 哪些 Prompt 可以复用，哪些必须重写。
10. 如何做到最终线路变化后定位 / Day / Route 自动局部刷新。
11. Revision / Undo 如何覆盖拖动、状态变化、住宿分界变化、多一晚等新操作。
12. 新结构上线时如何清理旧测试数据并初始化新的空数据环境。

明确不再需要回答：

```text
旧旅行如何迁移
旧计划 JSON 如何兼容
旧 Revision 如何恢复
新旧结构如何双写
```

---

# 28. 本轮验收目标

完成本计划后，用户应该感受到：

```text
我先填写旅行需求
→ 进入最终线路
→ AI 先生成主要停留 / 住宿节点
→ 我直接在线路上调整
→ 我可以生成详细地点
→ 详细地点直接进入对应日程
→ 我继续拖动、待定、不去、住 / 不住 / 多一晚
→ 地图和路线自动跟着变
→ 只有我明确要求时 AI 才优化已有顺序
```

用户不再需要理解：

```text
Step 2 候选
Step 3 Skeleton
Step 4 Detail Interest
Step 5 Day Stop
Macro / Detail 同步
stayDays
旧数据迁移
旧结构兼容
```

---

# 29. 数据重置验收原则

因为所有现有数据都是测试数据，本轮允许用以下方式完成新结构切换：

```text
删除旧测试旅行
清空旧数据库
重建数据库 schema
重新创建旅行
重新生成地点和日程
```

因此验收重点是：

```text
新建旅行是否正确
新结构是否简单一致
最终线路是否唯一
人工操作是否稳定
AI 权限是否正确
Day / 地图 / Route 是否自动跟随
Revision / Undo 是否对新数据工作
Provider 事实边界是否保持
```

不要把时间投入在旧测试数据迁移成功率上。

---

# 30. 下一步施工原则

后续实施方案必须遵守：

1. 不再为了兼容旧测试数据增加代码。
2. 如果已经写了只为旧数据兼容服务的过渡代码，应评估删除，而不是继续扩展。
3. 可以直接设计最简单的新旅行计划结构。
4. 可以直接升级或重建测试数据库结构。
5. Day / Route 只围绕最终线路工作，不再维持旧五步的双向同步。
6. Revision / Undo 从新结构开始重新保证。
7. 每个 Phase 按 `PLAN_IMPLEMENTATION_PROMPT.md` 要求交给用户本地 Codex 测试。
8. 测试只验证指定 Git Branch + HEAD。

下一步应根据本 PLAN 重新检查 `PLAN_EXECUTION.md` 和 `PLAN_PROGRESS.md`：

> **删除旧数据兼容、旧 Revision 恢复、新旧结构双写等已经不再需要的施工内容，然后继续实现更简单的新结构。**

# 31. 追加目标：最终线路 UI 从“配置表单”改成“可读的旅行线路”

前 1–30 节对应的 finalRoute、Day、Route、AI 权限和 Provider 边界已经成为本轮后续 UI 优化的基础。

本次追加改造**不重新设计 finalRoute 数据模型**，重点只解决当前最终线路的可读性和操作逻辑：

```text
地点 = 地点块
交通 = 两个当前有效地点之间的连接条
住宿 = Day 分界
Day = 高于地点块一级的日程块
编辑 = 显式按钮打开独立编辑抽屉
地图 = 与地点列表联动，但不抢夺编辑入口
```

目标是让用户看一眼就能理解：

> **我今天去哪些地方、地点之间怎么走、走多远、多久、晚上住在哪里。**

不能再让地点一点击就把大量表单直接撑在地点下面。

# 32. 最终线路的视觉层级固定为：Day → 地点 → 交通

最终线路右侧的核心结构改为：

```text
Day 1 · 日期 · 当日路线摘要

地点 A

    🚗 自驾 · 72 km · 58 分

地点 B

    🚶 步行 · 1.2 km · 16 分

地点 C【住】

Day 2 · 日期 · 当日路线摘要
...
```

必须坚持：

```text
Day 是一级结构
地点块是二级结构
交通条是地点之间的连接关系
```

交通不能再伪装成一个地点属性表单，也不能做成和地点块同等级的大卡片。

# 33. 两个地点之间恢复非卡片式交通条

当前“到达这里的交通方式”被藏在地点展开编辑区中，下一版必须恢复为线路中的可见连接关系。

交通条放在两个**当前有效地点**之间，基础样式类似：

```text
        🚗 自驾 · 72 km · 58 分
        ─────────────────
```

交通条默认展示：

```text
交通方式
Provider 返回的距离
Provider 返回的时间
```

规则：

1. 交通方式仍然保存在“到达当前节点”的 `transportFromPrevious` 上，不改变现有数据语义。
2. 用户点击交通条，只修改这一段的交通方式。
3. 距离、时长、geometry 继续只能来自 Route Provider，不能让用户或 AI 手工伪造。
4. Route 尚未计算时显示“路线待计算 / 更新中”，不能编造数字。
5. Route dirty 时不能把旧距离和旧时间伪装成当前事实；应明确显示“路线更新中”或旧数据状态。
6. Route Provider 失败时地点和交通方式仍保留，交通条显示“路线暂不可用”。
7. 交通条不是卡片，不增加厚重边框和大面积背景。

特别注意：

> **交通条表达的是当前有效线路，不是页面 DOM 中上下两个视觉相邻地点。**

例如：

```text
A
X【待定】
B
```

当前有效线路是：

```text
A → B
```

因此应显示 A → B 的真实交通，不允许错误显示 A → X 或 X → B 的有效交通。

当中间存在待定 / 不去地点时，可以明确标出来源和目标，例如：

```text
X【待定】
暂不参与当前路线

🚗 A → B · 35 km · 42 分

B
```

实现时应从当前派生 Day + `routeStates.route.legs` 构建专门的“有效交通连接 ViewModel”，不能简单依赖 `rows[rowIndex - 1]`。

Day 结束节点在派生 Day 中可能对应 `endAnchor`，普通中途节点对应 `stop.id`，因此 RouteLeg 映射不能只假设 `leg.toNodeId === finalRouteNode.id`；必须按现有 Day / Anchor / Stop 派生规则正确匹配。

# 34. 地点块 Hover / Click / Edit 必须是三个不同动作

当前一个 `selectedNodeId` 同时控制地点选中、地图飞行和展开编辑，下一版必须拆开。

## 34.1 Hover 地点块

鼠标移动到地点块上：

```text
地点块轻微高亮
对应地图 Marker 同时高亮
```

但绝对不能：

```text
移动地图
改变地图中心
改变缩放级别
打开编辑框
触发业务修改
```

鼠标移开以后恢复 Hover 高亮。

## 34.2 Click 地点块

点击地点块：

```text
地图 flyTo 当前地点
调整到适合查看这个地点的缩放级别
对应 Marker 保持选中高亮
```

点击地点块的职责就是：

> **在地图上看这个地点。**

点击地点块本身不再打开编辑表单。

## 34.3 Click“编辑”按钮

地点块必须提供独立、明确的“编辑”按钮。

点击“编辑”：

```text
不因为这个点击触发地图 flyTo
打开当前地点的编辑抽屉
```

因此最终语义固定为：

```text
Hover 地点 = 只高亮对应地图点
Click 地点 = 地图飞过去
Click 编辑 = 打开地点编辑抽屉
Click 交通条 = 编辑交通方式
Click 住 / 不住 / 多一晚 = 修改 Day 分界
```

所有按钮事件必须阻止冒泡，不能因为点“编辑”“住”“状态”等按钮顺便触发地点块 Click 的地图飞行。

---

# 35. UI 状态拆成 hover / map selection / editing 三层

前端不再使用一个 `selectedNodeId` 同时表达所有 UI 状态。

至少需要在 UI 层明确区分：

```text
hoveredNodeId
地图当前选中 / 聚焦的 nodeId
editingNodeId
```

具体命名可以根据代码结构调整，但语义必须分离。

规则：

- Hover 变化只影响轻量高亮。
- 地点 Click 改变地图选中 / 聚焦状态，并触发 flyTo。
- 打开 / 关闭编辑抽屉只改变 editing 状态。
- 地图 Marker Click 可以改变地图选中状态，但不能自动打开业务编辑抽屉。
- 编辑抽屉关闭后，地图选中状态不要求一起清空。
- 切换旅行或离开最终线路工作区时，editing / hover 临时状态应清理。

# 36. 地点详细信息改为独立编辑抽屉，不再向下撑开列表

当前地点选中后在地点下面展开：

```text
地点状态
住宿
交通
详细安排
地点信息
Google Maps
删除
```

下一版取消这种 inline 大表单。

桌面端点击地点块上的“编辑”以后，编辑框从**最终线路列表的左侧向地图方向抽出**，覆盖地图的一部分空间，不改变地点列表宽度，也不能把后续地点向下推。

抽屉只编辑“当前地点自身”的内容：

### 行程安排

```text
活动说明
时段
开始时间
结束时间
停留时间
备注
```

### 地点信息

```text
中文名称
英文名称
当地名称
地点类型
```

### 地图定位

```text
当前定位状态 / 地址
重新识别
地图选点
Google Maps 链接
```

### 危险操作

```text
从当前线路移除
```

交通方式不放进地点编辑抽屉，交通只通过地点之间的交通条编辑。

抽屉交互：

```text
点 A 的编辑 → 打开 A
点 B 的编辑 → 抽屉直接切换成 B
再点当前地点的编辑 → 收回
点关闭按钮 → 收回
按 Esc → 收回
切换旅行 / 工作区 → 收回
删除当前节点成功 → 收回
```

点击地点块本身不会收起 / 打开抽屉，只负责地图定位。

窄屏 / 移动端没有足够左侧空间时，可以改成覆盖式 Sheet / 全宽编辑层，但仍然禁止回退成地点下方 inline 展开。

# 37. 地图选点是编辑抽屉中的专门模式

用户在编辑抽屉点“地图选点”以后：

```text
编辑抽屉临时收起或进入紧凑状态
地图显示明确的选点提示条
用户在地图点位置
保存成功
恢复当前地点编辑抽屉，并展示新定位
```

选点期间不能让抽屉大面积遮挡地图。

取消选点后恢复原编辑地点上下文。

# 38. 住 / 不住 / 多一晚移到地点块主界面

住宿是 Day 的核心操作，不能再藏在地点编辑表单里。

普通地点块直接提供：

```text
+ 住
```

已经是住宿分界的地点显示：

```text
住 ▾
```

展开后至少提供：

```text
多一晚
不住
```

规则继续使用现有 finalRoute `endsDay` / `add_final_route_night` 行为，不新增 stayDays。

待定 / 不去地点如果保存了 `endsDay`，可以继续保留住宿标记的“暂不生效”视觉，但不能让用户误以为它正在切 Day。

# 39. Day 必须真正成为日程块

当前 Day 只是轻量 divider，下一版必须提高 Day 的视觉层级，让用户明显看出每天的范围。

每个 Day 顶部至少显示：

```text
Day N
日期
当天起点 / 终点或标题
当天 Route 可用时：总距离 / 总交通时间
Route dirty / attention 时：明确状态
```

Day 不是另一套可独立维护的数据；这些信息仍然根据 finalRoute 派生 Day 和 Route State 展示。

“多一晚”以后如果生成一个暂时没有中间详细地点的 Day，要明确显示空日程状态，例如：

```text
Day 4 · 陶波
这一天还没有详细安排
+ 添加地点
AI 补充详细地点
```

不能只让用户看到两个难以理解的重复“陶波”地点块。

# 40. 状态信息默认只显示异常，不重复系统正常状态

地点块默认不再长期显示：

```text
正常
已定位
```

这些是正常状态，不需要反复占空间。

只在需要用户注意时显示：

```text
待定
不去
未定位
定位中
路线需更新
```

待定和不去必须有明显不同的视觉表现，但不能用过度抢眼的大面积警告色破坏线路阅读。

---

# 41. 添加地点的插入位置必须显式

当前新增地点的位置依赖内部 selection，用户可能不知道新地点会插在哪里。

下一版必须让插入位置可见，例如：

```text
+ 在“陶波”后添加
```

或：

```text
+ 添加到线路末尾
```

不能让一个用户不可见的旧 selection 决定插入位置。

如果编辑抽屉和地图选中使用独立状态，添加地点也不能偷偷依赖 `editingNodeId` 或地图选中状态，除非按钮文案明确告诉用户插入位置。

# 42. 排序交互减少重复入口

桌面端地点排序以明确的拖动手柄为主：

```text
⠿ 地点名称
```

只有拖动手柄负责拖动，避免整个地点块都 `draggable` 导致误操作。

长期显示的“上移 / 下移”按钮可以从桌面主视图移除或降级到更多菜单；移动端如果拖动体验不足，可以保留上移 / 下移。

排序后的 Day / Route / 交通条继续按 finalRoute 的现有自动刷新规则更新。

# 43. AI 操作降级为辅助，不持续挤占线路

AI 继续是辅助工具，不应该让每个 Day 顶部长期堆满多个按钮。

建议收敛成：

```text
Day N                                      AI ▾
```

菜单中包含：

```text
补充详细地点
完善这一天
优化这一天
```

全程级别保留一个 AI 菜单，包含：

```text
生成详细地点
优化这一段
优化全程
```

Pending AI Proposal 可以显示为紧凑提示：

```text
✨ AI 有一个“Day 4 顺序优化”方案    查看
```

已采用 / 已拒绝 / 已撤销的方案不应长期用大卡片把最终线路往下推，可进入历史或折叠区域。

这部分属于次级 UI 优化，不能破坏当前 AI 权限边界。

# 44. 删除优先使用可撤销反馈

当前浏览器 `window.confirm` 与产品整体交互不一致。

在现有 Revision / Undo 能力允许的前提下，地点移除优先改成：

```text
Hobbiton 已从线路移除    撤销
```

如果本阶段实现成本明显扩大，可以先保留二次确认，但必须使用产品内确认 UI，不能新增另一套复杂删除逻辑。

无论 UI 如何，删除仍然只删除当前这一次 route node，不得顺带删除同 Place 的其他线路节点。

```text
→ A 地点块高亮
```

```text
→ Marker 保持选中

```

## 场景 C：编辑是独立入口

# 47. 本次追加改造的技术原则

1. 默认只改前端展示与 UI 状态，不重构 finalRoute / Day / Route 的服务端核心模型。
2. 交通距离和时长优先复用现有 `routeStates.route.legs`，禁止前端自行估算真实路线事实。
3. Day 摘要优先复用现有派生 `plan.days` 和 DayRoute，不维护第二份 Day UI 数据。
4. hover / map selection / editing 是前端临时状态，不写入旅行文档和 Revision。
5. 用户真正修改状态、住宿、排序、交通、地点资料时，继续走现有 command / API / generation 保护。
6. 地图仍然不是第二业务 mutation 入口；Marker Click 只能选择 / 聚焦，不直接修改线路。
7. 本次施工应优先补充可测试的纯函数 ViewModel：Day 分组、有效交通连接、RouteLeg 映射、异常状态展示等，减少 JSX 中临时推导。
8. 每个施工 Phase 完成后继续遵守 `PLAN_IMPLEMENTATION_PROMPT.md`：施工 Agent 不运行测试，必须冻结 Branch + HEAD 后交给用户本地 Codex 验证。
