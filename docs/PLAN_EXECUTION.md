# 1. 目标

本次改造的最终目标是：

```text
用户填写旅行需求
→ 进入“最终线路”
→ AI 生成主要地点并直接进入最终线路
→ 用户直接在线路中排序、待定、不去、住 / 不住 / 多一晚
→ 用户生成详细地点，详细地点直接插入最终线路
→ 日程、地图、交通路线都根据最终线路自动变化
→ 只有用户明确要求“优化”时，AI 才能重排已有地点
```

产品完成后，用户不再维护 Step 2 Candidate、Step 3 Skeleton、Step 4 Detail Interest、Step 5 Day Stop 四套互相同步的内容。

系统真正保存并由用户维护的线路只有一份：**最终线路**。

# 2. 与本次改造直接相关的当前状态

当前产品仍是五步：

```text
Step 1 旅行需求
Step 2 想去哪些地方
Step 3 路线和天数
Step 4 补充景点
Step 5 每日行程
```

当前代码同时维护：

```text
Place
Candidate
Skeleton / Stay Block / stayDays
Day / Anchor / Stop
Macro Route
Detail Route
itineraryUpdateState
```

当前 Step 3 的 `stayDays` 会真正展开成多个 Day；Step 4 新增地点后仍需要 Step 5 再安排成 Stop。

当前数据库版本为 3，旅行计划 JSON 为 schemaVersion 2。数据库表中直接保存完整旅行计划 JSON，历史 Revision 同样保存完整计划 JSON。

因此本次需要同时解决：

1. 新的最终线路数据结构；
2. 旧旅行计划读取和转换；
3. 历史 Revision 继续可读、可恢复；
4. Day / 路线从最终线路自动生成；
5. UI 从五步收敛为“旅行需求 + 最终线路”；
6. AI 生成、插入和优化权限重新定义。

# 3. 已确认的关键设计决定

## 3.1 用户只维护最终线路

最终线路是一份有稳定顺序的“线路节点”数组。

一个线路节点表示：

> 某个现实地点在这趟最终线路中的一次出现。

同一个 Place 可以在线路中出现多次。

例如“陶波多住一晚”允许表示成：

```text
A
→ 陶波 #1【日程分界】
→ 陶波 #2【日程分界】
→ B
```

两个“陶波”线路节点引用同一个 Place，但拥有不同的线路节点 ID。

因此不需要重新引入 `stayDays=2` 这样的地点属性。

## 3.2 Place 继续表示现实地点

现有 Place、PlaceResolution 和地图 Provider 事实边界继续保留。

线路节点只引用 Place，不复制地图 Provider 的坐标、距离、时长或 geometry。

一个 Place 可以只有一个定位结果，但可以被多个线路节点引用。

## 3.3 最终线路节点需要保存的最小信息

施工时以现有类型命名风格落地，但语义至少包括：

```text
id                 稳定线路节点 ID
placeId            引用现实 Place
status             normal / tentative / no_go
endsDay             该节点后是否形成日程分界
transportFromPrevious  从“上一个当前有效节点”到这里的交通方式及用户输入
```

如现有 DayStop 中确有需要保留的活动、时间、备注、费用等详细信息，可迁移到线路节点的可选详细信息中，避免用户详细规划能力倒退。

## 3.4 待定 / 不去不改变排序

三个状态：

```text
正常
待定
不去
```

待定和不去都继续保留在线路和地图中，只是不参与当前有效日程与交通线路。

恢复正常后直接在原排序位置重新生效。

“移除”才真正删除线路节点。

## 3.5 已确认：待定 / 不去时住宿分界暂时失效

如果：

```text
A → B【住】 → C
```

B 改为待定或不去后：

```text
当前有效线路：A → C
```

B 仍保留原顺序和 `endsDay` 设置，但该分界暂时不参与 Day 划分。

B 恢复正常后，原来的住宿分界一起恢复。

## 3.6 已确认：交通方式属于“到达当前节点”

每个线路节点保存“从上一个当前有效地点怎么到我这里”。

例如：

```text
A —自驾→ X —步行→ B
```

X 改为不去以后，当前线路成为：

```text
A —步行→ B
```

也就是说 B 自己保存的交通方式继续作用于新的上一有效地点 A。

X 恢复以后：

```text
A —自驾→ X —步行→ B
```

X 与 B 原有的交通设置都不需要重写。

## 3.7 “住 / 不住 / 多一晚”只机械修改线路

### 住

给当前正常线路节点增加日程分界。

### 不住

只取消当前节点的日程分界，不删除地点、不移动地点、不让 AI 自动重排。

例如：

```text
Day 1：A → B【住】
Day 2：B → C → D【住】
```

B 改为不住后：

```text
Day 1：A → B → C → D【住】
```

### 多一晚

在当前节点后插入一个新的线路节点，引用同一个 Place，并在新节点后形成新的日程分界。

例如：

```text
A → 陶波【住】 → B
```

多一晚后：

```text
A → 陶波【住】 → 陶波【住】 → B
```

不会自动移动已有景点。

## 3.8 Day 是最终线路的自动结果

用户不直接维护 Day 编号。

系统根据：

```text
旅行起点
+
所有 normal 线路节点
+
normal 节点中生效的日程分界
```

自动形成 Day。

待定 / 不去节点完全跳过。

最后一天允许没有住宿分界。

Day 编号按当前线路自动连续计算。

底层如需稳定 Day ID，优先由形成该 Day 的稳定线路节点 ID 派生或稳定复用，不让用户手工维护。

## 3.9 Day / 路线可以保留为系统自动生成结果，但不能再独立编辑

为尽量复用当前稳定的地图、路线和 Day UI 基础设施，施工过程中允许继续生成现有 `days[]` / DayRoute 结构供现有代码读取。

但必须保证：

> `days[]` 只能由最终线路统一生成，不能再成为另一份可独立修改的线路数据。

任何旧的 `set_day_anchor`、`move_day_stop`、Skeleton 保存等入口，在新流程接管后必须停止作为用户线路修改入口。

## 3.10 Candidate 退出现有用户线路职责

Candidate 可以在过渡期继续存在，用于：

```text
旧数据读取
AI 研究过程
兼容尚未改造的内部代码
```

但新的：

```text
生成主要地点
生成详细地点
手动新增地点
```

最终结果必须直接写入最终线路。

用户不再需要进入独立 Candidate 页面，再进行第二次“采用/安排”。

## 3.11 旧数据兼容

数据库表结构若不需要改变，优先保持数据库 `user_version = 3`，只升级旅行计划 JSON 的结构，并提供旧 schema 读取转换。

旧旅行计划读取时：

### 已有 Day 的旅行

优先把用户已经形成的真实 Day 路径转换成最终线路：

```text
每一天的 Stops
+
当天终点
+
当天是否为最后一天
```

旧 Day 的终点形成对应日程分界；最后一天不强制增加住宿分界。

线路节点尽量复用旧 Stop / Anchor 的稳定 ID，减少 Revision、选择状态和测试中的无意义变化。

### 还没有 Day 的旅行

不得因为技术迁移而丢失 Candidate。

初始转换按旧 Candidate 顺序保留地点：

```text
must_go / want_to_go → normal
optional              → tentative
excluded              → no_go
```

此时不自动添加住宿分界；用户可以继续手工调整或重新生成主要地点。

### 历史 Revision

旧 Revision 必须继续能查看和恢复。

恢复旧 Revision 时先读取旧结构并转换成新结构，再作为新的当前版本保存；不原地改写历史 Revision 内容。

## 3.12 Provider 事实边界不变

继续保留：

```text
地点可先保存、后定位
定位失败不自动删除
不自动补位
正常 / 待定 / 不去都可以定位并显示在地图
真实坐标、距离、时长、geometry 只能来自地图 Provider
```

## 3.13 AI 权限边界

### 生成主要地点

AI 可以：

```text
新增地点
决定新地点插入最终线路的位置
建议日程分界
```

不能因为“生成”而重排用户已经存在的线路节点。

### 生成详细地点

AI 可以在用户指定范围内新增线路节点，并决定新节点插在哪两个既有节点之间。

不能：

```text
改变已有节点相对顺序
删除已有节点
修改已有节点状态
修改已有住宿分界
把已有节点移动到其他 Day
```

### 优化

只有用户明确触发：

```text
优化这一天
优化这一段
优化全程
```

AI 才能在对应范围重排已有线路节点。

未授权范围保持不变。

## 3.14 右侧是唯一业务操作入口

保留现有设计原则：

```text
地图 = 展示 / 选择 / 定位辅助
右侧 = 业务操作
```

地图 Popup 不增加第二套删除、偏好、生成、住宿或优化入口。

# 4. 实施阶段

本次施工压缩为 3 个 Phase。

原则：

- Phase 1 先把底层规则做完整，由自动测试覆盖，不要求用户重复手测底层。
- Phase 2 一次完成主要人工交互闭环，用户进行第一次 UI 验收。
- Phase 3 再接 AI 生成 / 优化并清理旧五步职责，用户进行最终端到端验收。

# Phase 1：最终线路、旧数据兼容与自动 Day / Route 基础

## 目标

完成后，系统底层已经能够只根据一份最终线路稳定得到当前 Day 和路线输入，并能安全读取旧旅行和旧 Revision。

此阶段不要求新 UI 已经完整上线。

## 修改范围

- 数据模型
- 后端合同
- 旅行计划读取 / 写入
- 旧数据兼容
- Day 自动生成
- Route dirty / 刷新依赖
- PlanCommand / Revision 基础
- 自动测试

## 主要修改

1. 为旅行计划增加有序的最终线路节点结构。
2. 支持同一 Place 多次出现，每次有独立线路节点 ID。
3. 增加 normal / tentative / no_go 状态。
4. 增加 `endsDay` 日程分界。
5. 将交通方式定义为当前节点的 `transportFromPrevious`。
6. 实现纯函数：最终线路 → 当前有效线路 → Day。
7. 实现：住 / 不住 / 多一晚 / 拖动 / 状态切换 / 新增 / 移除 的确定性底层操作。
8. Day 编号和日期自动重算。
9. 路线输入改为读取自动生成的 Day 节点顺序。
10. 旧 schemaVersion 2 旅行计划读取后转换为新结构。
11. 旧 Revision 读取和恢复继续工作。
12. 保持数据库安全边界、generation / revision / CAS、Provider 事实边界。
13. 增加结构约束：禁止未知 Place 引用、重复线路节点 ID 等数据损坏。
14. 防止旧 Skeleton / DayStop 命令继续形成与最终线路不一致的第二套用户线路。

## 完成条件

- 同一 Place 可以在线路中重复出现。
- `多一晚` 能稳定形成“同地点 → 同地点”的新 Day。
- `不住` 只合并 Day，不移动其他节点。
- tentative / no_go 节点保留排序但不参与当前 Day 和 Route。
- tentative / no_go 节点的日程分界暂时失效，恢复 normal 后恢复。
- 跳过中间节点后，后一节点自己的交通方式用于新的上一有效节点。
- 最后一天没有住宿分界也合法。
- 修改日程分界后 Day 编号连续重算。
- 旧旅行和旧 Revision 可读取、可恢复。
- 数据库不因旧计划 JSON 而拒绝启动。
- 现有 revision / undo 基础仍然有效。

## 自动测试

至少运行：

```text
npm run typecheck
npm test
npm run build
```

并新增 / 更新针对以下场景的测试：

```text
最终线路 schema
旧 schemaVersion 2 → 新结构转换
旧 Revision 恢复
同一 Place 多线路节点
住 / 不住 / 多一晚
normal ↔ tentative ↔ no_go
日程分界在 tentative / no_go 时暂时失效
交通方式继承规则
最后一天无住宿
Day 编号 / 日期重算
路线 dirty 范围
generation / revision 冲突
Provider 事实边界
```

## 用户测试

无需用户手动测试，本阶段由自动测试覆盖。

# Phase 2：右侧“最终线路”人工规划闭环 + 地图联动

## 目标

用户可以不依赖 AI，直接在右侧完成一整趟最终线路的人工调整，并实时看到 Day 和地图路线变化。

这是第一次需要用户实际体验的阶段。

## 修改范围

- 前端工作流
- 最终线路 UI
- 右侧交互
- 地图展示
- 路线显示
- 定位修复
- Advisory
- API
- 自动测试
- UI 手工验收

## 主要修改

1. 五步导航收敛为：

```text
规划：旅行需求
行程：最终线路
```

2. 新增统一最终线路面板。
3. 最终线路按真实顺序展示所有节点。
4. 支持拖动排序。
5. 支持：

```text
正常
待定
不去
编辑
移除
住
不住
多一晚
交通方式
定位修复
```

6. 每个 Day 直接由线路分界展示，Day 中允许多个地点。
7. 多一晚后立刻出现空的“同地点 → 同地点”日程块。
8. 地图显示 normal / tentative / no_go 全部地点并视觉区分。
9. 地图交通线只显示当前 normal 节点形成的路线。
10. 地图和 Day 随最终线路变化自动刷新，不要求用户理解 dirty / Macro / Detail 状态。
11. 业务操作全部保留在右侧，地图 Popup 只承担展示 / 选择 / 定位辅助。
12. 把旧 Candidate / Skeleton / Step 4 / Step 5 页面从正常用户流程中移除。
13. 已能由最终线路自动判断的问题使用 Advisory，不自动纠正用户方案。

## 完成条件

用户无需 AI 即可完成：

```text
新增地点
→ 排序
→ 设为待定 / 不去 / 恢复
→ 设置住 / 不住
→ 多一晚
→ 调整交通
→ 删除
→ 修复定位
→ 查看 Day
→ 查看地图和交通路线
```

并且整个过程只有右侧一套业务入口。

# Phase 3：AI 生成 / 局部补充 / 优化 + 旧流程清理

## 目标

把原 Step 2 和 Step 4 的 AI 生成能力直接接入最终线路，并把 AI 重排权限严格限制在用户明确授权的优化范围内。

完成后达到 PLAN 的完整目标状态。

## 修改范围

- AI Action
- Action Scope
- Prompt
- 主要地点生成
- 详细地点生成
- 局部生成
- AI 优化
- Proposal / Revision / Undo
- 旧 Skeleton / Candidate / Detail 流程清理
- 前端 CTA
- 自动测试
- 端到端验收
- PRODUCT / TECHNICAL 文档收尾更新

## 主要修改

1. “生成主要地点”直接新增最终线路节点。
2. 首次生成不得把“AI 生成了地点”等同于“默认住一晚”。
3. AI 可以建议并返回明确住宿分界，但必须作为生成结果中的显式决定。
4. “生成详细地点”直接把新地点插入最终线路对应位置。
5. 新增地点时只允许插入，不允许改变已有节点相对顺序。
6. 支持对：

```text
某个 Day
某一段线路
某个住宿点附近
```

进行局部详细地点生成。
7. 增加 / 改造 AI Scope，使生成与优化操作明确区分。
8. “优化这一天 / 这一段 / 全程”才允许重排已有节点，并且只能改授权范围。
9. 生成不得擅自删除、改状态、改住宿分界或移动范围外节点。
10. Proposal / Revision / Undo 覆盖最终线路新增、排序、状态、住宿分界等操作。
11. 重写相关 Prompt 和 Action 合同。
12. 删除或隔离已经没有产品职责的 Skeleton / stayDays / Step 4→Step 5 二次安排 / Macro-Detail 同步入口。
13. 更新 `PRODUCT.md` 和 `TECHNICAL.md`，把完成后的实际状态写成新的当前现状。


# 5. 高风险点与施工约束

## 高风险 1：旧旅行和 Revision

不能只让“新建旅行”工作。

任何 schema 调整都必须同时验证：

```text
旧 current_plan_json
旧 plan_revisions.plan_json
恢复旧 Revision
复制旧旅行
```

## 高风险 2：最终线路与 Day 出现两份可编辑状态

过渡期允许继续产生 `days[]` 供现有地图 / 路线代码读取，但必须由最终线路统一生成。

如果任何用户操作仍然可以直接改 Day / Stop 而不回写最终线路，该 Phase 不算完成。

## 高风险 3：AI 借“生成”重排已有线路

生成和优化必须是不同权限。

测试必须比较操作前后的已有线路节点顺序，不能只检查“结果看起来合理”。

## 高风险 4：待定 / 不去与地图、住宿、交通出现不一致

状态切换后必须同时验证：

```text
线路列表顺序
Day 划分
住宿分界是否生效
交通连接
地图点显示
地图路线显示
恢复状态后的还原
```

## 高风险 5：范围扩大

局部生成 / 局部优化不得因为实现方便自动扩大成整趟修改。

现有 Scope / generation / CAS / Revision 能力优先复用。

# 6. 施工原则

- 只做 PLAN 所需修改，不顺手做无关重构。
- 任何旅行合理性问题都优先提示，不自动修改用户方案。
- 自动测试能覆盖的内容不交给用户重复测试。
- 每完成一个 Phase，立即同步 `PLAN_PROGRESS.md`。
- Phase 2 和 Phase 3 用户测试通过前，不提前宣布整轮完成。
- 如果施工中出现新的、会改变产品行为的问题，停止该决定相关施工并记录到 `PLAN_PROGRESS.md`，不能偷偷增加新的产品规则。
