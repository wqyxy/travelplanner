# TravelPlanner 最终线路 UI 交互规范

> 状态：**当前产品交互目标**  
> 更新日期：2026-09-05  
> 文件名保留“五步 UI 交互规范.md”仅为兼容已有链接；内容已不再采用五步产品结构。  
> 本文件只定义 UI / 用户交互，不是技术施工文档。

---

# 1. 核心原则

最高优先级：

> **用户只维护一份最终线路；地图 / 日程负责展示和选择，右侧控制台负责所有业务操作。**

同时保持：

> **手工优先，AI 不因为“更合理”而擅自改用户已经排好的线路。**

用户不需要理解：

```text
Backbone
Skeleton
Macro / Detail
Planning Area
Core Visit
Detail Interest
stayBlockId
fingerprint
macroDirty
affectedDayIds
CAS
Resolution
```

---

# 2. 顶层导航

新的顶层只保留两个核心工作区：

```text
旅行需求
最终线路
```

不再显示五步导航。

初次创建时先填写旅行需求，然后进入最终线路。

已经有行程的旅行，默认更适合直接进入“最终线路”。

---

# 3. 页面结构

桌面端继续使用：

```text
┌──────────────────────────────┬───────────────────────────┐
│                              │ 顶层导航                  │
│       地图 / 日程 / 路线     │───────────────────────────│
│       展示 + 选择            │ 当前选中对象              │
│                              │ AI / 状态 / 操作          │
│                              │ [唯一 Primary CTA]       │
└──────────────────────────────┴───────────────────────────┘
```

地图 / 日程不成为第二套编辑器。

右侧控制台负责：

```text
生成主要地点
生成详细地点
待定 / 不去
编辑 / 移除
住宿分界
增加一天
交通方式
定位修复
AI 优化
```

同一个业务动作只有一个 canonical 入口。

---

# 4. 最终线路主视觉

最终线路按一条线性顺序展示。

例如：

```text
奥克兰
↓
Hobbiton
↓
罗托鲁瓦  [住宿分界]
↓
Wai-O-Tapu
↓
陶波
↓
惠灵顿    [住宿分界]
```

地点块之间显示交通连接段。

连接段可以展示：

```text
交通方式
Provider 距离
Provider 时长
待计算 / 待定位状态
```

Provider 尚未返回事实时，不复用旧数据冒充当前线路结果。

---

# 5. 地点块统一

原 Step 2 和 Step 4 的地点卡片统一迁入最终线路。

每个地点块主要显示：

```text
地点名称
必要摘要
定位状态
当前状态
住宿分界状态（如果有）
```

右侧主要偏好操作只保留：

```text
待定
不去
```

并保留：

```text
编辑
移除
```

不再提供“必去 / 想去 / 可选 / excluded”四级按钮系统。

---

# 6. 正常 / 待定 / 不去的视觉与行为

最终线路里的地点不因为待定或不去而离开列表。

### 正常

- 正常颜色。
- 参与 Day 划分和实际交通路线。

### 待定

- 地点块深灰色。
- 仍保留原排序。
- 地图仍显示标记。
- 不参与当前交通路线。
- 不参与当前 Day 的有效线路计算。

### 不去

- 另一种深灰 / 弱化样式，与待定可区分。
- 仍保留原排序。
- 地图仍显示标记。
- 不参与当前交通路线。
- 不参与当前 Day 的有效线路计算。

用户把待定 / 不去恢复为正常后，地点直接在原位置恢复参与线路。

“移除”与“不去”必须明显不同：

```text
不去 = 保留在线路列表
移除 = 从最终线路真正删除
```

---

# 7. 地图规则

地图只读最终线路列表。

所有仍在最终线路中的地点都显示：

```text
正常
待定
不去
```

三种状态使用不同视觉。

实际路线只连接正常地点。

例如：

```text
A
X（待定）
B
Y（不去）
C
```

地图显示 5 个点，路线显示：

```text
A → B → C
```

地图点选只负责：

```text
选中地点
→ 右侧显示对应详情
```

地图 Popup 不再放偏好、删除、生成、定位修复等业务按钮。

---

# 8. 第一次生成：生成主要地点

最终线路为空时，Primary CTA：

```text
[生成主要地点]
```

AI 生成这趟旅行的主要住宿 / 停留地点及建议顺序，并直接进入最终线路。

不能把这一步描述成“先生成候选，再去下一步采用”。

重要：

> **生成主要地点不代表每个地点默认住 1 晚。**

UI 不出现地点级“住几晚”输入框。

---

# 9. 日程块不是独立规划结果

Day 是最终线路按住宿分界切出来的视图。

核心规则：

> **两个有效住宿分界之间的所有正常地点属于同一个 Day。**

例如：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦 [住]
→ Wai-O-Tapu
→ 惠灵顿 [住]
```

显示为：

```text
Day 1
奥克兰 → Hobbiton → 罗托鲁瓦
住宿：罗托鲁瓦

Day 2
罗托鲁瓦 → Wai-O-Tapu → 惠灵顿
住宿：惠灵顿
```

不做额外的“把某个地点归到某一天”的人工同步动作。

---

# 10. 住宿操作

住宿是线路分界，不是地点类型，也没有“住几晚”字段。

选中适用地点后，右侧可以提供自然操作：

```text
住
多一晚
不住
```

### 住

把当前位置设为一个日程结束分界。

### 多一晚

直接增加一个新的日程块。

例如：

```text
Day 3：A → 陶波
Day 4：陶波 → B
```

点击“多一晚”后：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

新增的 Day 允许暂时为空。

### 不住

只取消当前位置的住宿分界，不删除地点。

例如：

```text
Day 1：A → B [住]
Day 2：B → C → D [住]
```

B 改为“不住”后：

```text
Day 1：A → B → C → D [住]
```

系统不能因为这一天过长而自动修正。

---

# 11. Day 编号

Day 编号始终由当前有效住宿分界和旅行终点自动连续计算。

用户改变住宿分界后，Day 1 / Day 2 / Day 3 立即重新编号。

UI 不承诺“原 Day 3 永远叫 Day 3”。

第一天从旅行起点开始，到第一个住宿分界结束。

最后一天允许以机场、车站、城市或其他旅行终点结束，不要求再制造住宿点。

---

# 12. 同一地点连续多日

UI 不出现：

```text
陶波 · 住 2 晚
```

作为一个可编辑属性。

如果实际连续停留两晚，直接展示两个 Day。

例如：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

后来详细地点加入 Day 4 后，可以自然显示：

```text
Day 4：陶波 → Huka Falls → Tongariro → 陶波
```

“连续住几晚”如果需要展示，只能作为从 Day 结果计算出来的摘要，而不是编辑字段。

---

# 13. 拖动排序

所有地点块在最终线路里保持明确顺序，并支持拖动手柄排序。

用户一旦手工排序，当前顺序就是 canonical 用户决定。

AI 不得因为地理上更合理而自动改回来。

待定 / 不去的地点同样保留排序位置，也可以被用户拖动。

排序变化后：

```text
日程视图重新派生
地图标记保持
正常地点路线自动刷新
```

不要求用户额外点“重新生成整条线路”。

---

# 14. 第二次生成：生成详细地点

最终线路已有主线路后，可以在同一页面提供：

```text
[生成详细地点]
```

AI 生成原来 Step 4 的景点、活动、观景点、餐厅等，并直接插入最终线路。

例如：

```text
奥克兰
→ 罗托鲁瓦 [住]
→ 陶波 [住]
```

生成后：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦 [住]
→ Wai-O-Tapu
→ Huka Falls
→ 陶波 [住]
```

详细地点加入后直接属于对应 Day，不再需要“下一步生成每日行程”。

---

# 15. AI 自动插入的边界

新增详细地点时，AI可以决定：

> 新地点应该插在哪两个已有地点之间。

AI不能借机：

```text
交换已有地点顺序
删除已有地点
改变已有地点状态
改变已有住宿分界
把已有地点搬到别的 Day
```

例如原来：

```text
A → B → C → D
```

新增 X 后允许：

```text
X → A → B → C → D
A → X → B → C → D
A → B → X → C → D
A → B → C → X → D
A → B → C → D → X
```

但不能因为加入 X 而变成：

```text
A → C → X → B → D
```

除非用户明确要求 AI 优化。

---

# 16. 详细地点生成可以局部发生

“生成详细地点”不必只能全程执行一次。

可以支持用户选中：

```text
某个 Day
某一段线路
某个住宿地点附近
```

然后只补充对应范围。

未选中的其他线路保持不变。

---

# 17. 最终线路变化后自动更新

定位和线路生成只根据最终线路列表。

只要列表发生影响当前线路的变化，系统就自动更新相应展示。

包括：

```text
新增地点
详细地点插入
编辑地点
移除地点
拖动排序
待定 / 不去 / 恢复正常
住宿分界变化
增加 Day
交通方式变化
```

UI 不要求用户理解“上游变更导致下游过期”的五步依赖关系。

对用户来说就是：

> **我改了最终线路，地图和线路跟着变。**

---

# 18. 定位状态

地点可以先存在、后定位。

未定位时：

```text
地点仍留在线路列表
地图在无法显示真实坐标时明确标记状态
不自动删除
不自动补位
不伪造坐标
```

定位成功后地图自动更新。

正常、待定、不去都可以进行定位，因为三者都需要在地图上显示。

---

# 19. AI 优化

只有用户明确调用时，AI 才可以重新排列已有线路。

可以提供范围化操作：

```text
优化这一天
优化这一段
优化全程
```

AI 优化与“生成详细地点”必须区分：

```text
生成详细地点
= 只插新地点，保留已有节点相对顺序

AI 优化
= 用户授权后，可以调整授权范围内已有节点顺序
```

高影响优化应展示关键 Diff 后再应用。

---

# 20. 不合理安排的处理

用户手工形成的线路可以不合理。

例如：

```text
一天太长
一天地点太多
明显绕路
住宿分界奇怪
```

系统可以提醒：

```text
这一天可能较赶
这段驾驶时间较长
```

但默认不能：

```text
自动移动地点
自动增加住宿
自动删除地点
自动拆 Day
自动合并 Day
```

除非用户主动让 AI 优化。

---

# 21. Primary Button 规则

任意时刻最多一个主按钮。

常见优先级：

```text
1 当前真正需要的修复
2 当前最重要的生成 / 保存动作
3 AI 优化或下一项主要行动
```

例如：

最终线路为空：

```text
[生成主要地点]
```

已有主线路但尚未补细节：

```text
[生成详细地点]
```

选中某个 Day 且用户准备优化：

```text
[优化这一天]
```

不要同时摆出多个同层级 Primary CTA。

---

# 22. 右侧唯一入口示例

用户点击“陶波”后，右侧可以根据上下文显示：

```text
陶波

[待定] [不去]

住宿
[住] [多一晚] [不住]

[编辑]
[移除]
```

如果陶波是详细景点而不适合作为住宿分界，住宿区可以不显示。

地图 Popup 只显示摘要和选中状态，不复制这些按钮。

---

# 23. 移动端

窄屏继续采用：

```text
主视图 = 最终线路 / 日程
地图 = Tab / 抽屉
右侧控制台 = 底部抽屉 / 详情面板
```

仍然保持一个 canonical 业务入口，不因为移动端而复制操作。

---

# 24. 产品级 UI 验收

第一次使用的用户应该可以在不理解任何工程术语的情况下完成：

```text
填写旅行需求
→ 生成主要地点
→ 看见一条最终线路
→ 手工拖动地点
→ 设置住 / 多一晚 / 不住
→ 把地点设为待定或不去但仍保留在列表
→ 在地图看到全部地点及状态区别
→ 生成详细地点
→ 景点直接进入对应线路和 Day
→ 继续手工调整
→ 必要时主动让 AI 优化
```

必须满足：

```text
没有 Step 2 / Step 4 独立地点页面
没有 Step 3 / Step 5 两套行程需要同步
没有地点级“住几晚”编辑字段
待定 / 不去不会从最终线路消失
地图仍显示待定 / 不去
只有正常地点参与当前路线
生成详细地点不会重排已有节点
手工不合理不会被系统偷偷修正
最终线路变化后地图 / 路线自动跟随
业务操作仍集中在唯一控制台
```

# 25. 本文档边界

本文只回答：

> **用户看到什么、怎么操作、操作后应该发生什么。**

本文不回答：

```text
现有 Candidate / Day / Stop 怎么迁移
数据库字段怎么设计
stayBlockId 是否保留
API 如何重构
Prompt 如何改
缓存如何失效
哪些旧组件复用
施工 Phase 怎么分
```

这些属于下一步技术修改方案。
