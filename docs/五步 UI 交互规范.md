# TravelPlanner 五步 UI 交互规范

> 状态：**已确认的产品交互规范，尚未实施**  
> 更新日期：2026-09-02  
> 配套施工图：[`TravelPlanner 五步规划流程重构实施方案.md`](./TravelPlanner%20五步规划流程重构实施方案.md)

---

# 1. 核心原则

用户在任何时刻都应该知道：

```text
我现在在哪一步？
这一页要解决什么？
哪里可以修改？
修改后影响什么？
下一步应该做什么？
```

最高优先级规则：

> **地图 / 时间轴负责展示和选择；右侧控制台负责所有业务操作；同一个业务动作只有一个 canonical UI 入口；局部修改只让真正受影响的部分需更新。**

新增更高一层原则：

> **系统内部可以复杂，用户界面必须简单。内部状态、ID、依赖图、CAS、fingerprint、WorkflowStep 等都不直接要求用户理解。**

---

# 2. 五步用户流程

统一显示：

```text
1 旅行需求
2 想去哪些地方
3 路线和天数
4 补充景点（可选）
5 每日行程
```

不要要求用户理解：

```text
Backbone
Skeleton
Macro / Detail
Planning Area
Core Visit
planningRole
stayBlockId
fingerprint
macroDirty
affectedDayIds
requiresWorkflowStep
ConversationStage
Resolution
CAS
```

这些都是内部工程概念。

用户心智必须保持：

```text
我想怎么玩
→ 我想去哪些地方
→ 这些天怎么排
→ 要不要再补点景点
→ 每天具体怎么玩
```

---

# 3. 页面只有两个主要职责区

```text
┌──────────────────────────────┬───────────────────────────┐
│                              │ 五步导航                  │
│      地图 / 时间轴 / 路线    │───────────────────────────│
│      展示 + 选择             │ 当前步骤内容              │
│                              │ 当前对象详情              │
│                              │ AI / 状态 / 操作          │
│                              │ [唯一 Primary CTA]       │
└──────────────────────────────┴───────────────────────────┘
```

不新增独立左侧步骤栏。

地图 / 时间轴不提供：

```text
新增 / 删除
设置必去
角色调整
生成 / 更新 AI 结果
修复定位
推进步骤
```

右侧控制台负责全部业务入口。

---

# 4. 唯一入口，但不要让用户被“赶步骤”

业务动作唯一归属：

| 业务动作 | 归属步骤 |
|---|---|
| 修改旅行需求 | Step 1 |
| 停留区域 / 重要游览地 | Step 2 |
| 路线 / 天数 / Stay Block | Step 3 |
| 普通兴趣点 | Step 4 |
| 每日行程 / Stop / Day | Step 5 |
| 定位修复 | 对象归属步骤右侧详情 |

如果用户在错误步骤发起意图：

```text
识别 intent
→ 自动切换到归属步骤
→ 保留 selection / intent
→ 直接展示对应确认 / 建议 / 可执行入口
```

禁止反复显示：

```text
请前往第二步
请前往第三步
请前往第四步
```

正确体验示例：

用户在 Step 5 说：

```text
蒂阿瑙再加一天
```

系统直接切到 Step 3，并显示：

```text
蒂阿瑙 2 → 3 天
还需要从其他地方减少 1 天

建议：
皇后镇 4 → 3 天

[保存这个调整]
```

高影响 mutation 仍需确认，但“切换到正确工作区”本身可以自动完成。

---

# 5. 一个全局 selection

整个 App 只维护一个主要 selection：

```text
Planning Area
Core Visit
Detail Interest
Stay Block
Day
Stop
Route Segment
```

地图、列表、时间轴都只更新这一个 selection。

用户不看到 selection 类型名；只感受到“我点了哪个对象，右侧就在编辑哪个对象”。

---

# 6. Primary Button 规则

任意时刻最多一个 Primary Button。

优先级：

```text
1 真正阻塞当前任务的修复
2 当前步骤最重要的生成 / 更新 / 保存
3 下一步导航
```

Secondary / Menu 可以有：

```text
手动新增
查看原因
筛选
高级调整
全量重做危险操作
```

但不能与 Primary 抢层级。

---

# 7. Step 1：旅行需求

用户任务：

> 告诉系统我想进行什么旅行。

右侧显示：

```text
日期 / 天数
出发地
人数
交通偏好
节奏
主题 / 偏好
限制
明确想去的地方
```

完成后：

```text
[下一步：想去哪些地方]
```

只进入 Step 2，不自动生成地点。

需求变化若影响后续结构，用户只看到自然语言：

```text
路线和天数需要重新确认
```

不显示 `macroDirty`。

---

# 8. Step 2：想去哪些地方

用户任务：

> 先选出这趟旅行想考虑的停留地点和重要游览地。

页面顶部固定说明：

> **先选出想考虑的地方，下一步会根据总天数安排最终路线。**

这一步是“愿望清单”，不是最终路线。

## 没有候选

Primary：

```text
[帮我推荐地点]
```

## 已有候选

Primary：

```text
[下一步：路线和天数]
```

---

# 9. Preference：用户主要只操作“必去 / 想去”

数据层仍有：

```text
must_go
want_to_go
optional
excluded
```

但卡片主 UI 只强调：

```text
⭐ 必去
♡ 想去
```

普通 AI 推荐默认 `optional` 时：

```text
不需要给每张卡挂“可选”Badge
```

用户把“想去”取消时，可回到 optional。

用户“不想考虑”通过：

```text
移除
不考虑
```

表达，而不是要求选择 `excluded` 枚举。

因此一个普通候选可以只显示：

```text
瓦纳卡
```

用户点亮后才显示：

```text
瓦纳卡  ♡ 想去
```

或者：

```text
瓦纳卡  ⭐ 必去
```

---

# 10. 重要游览地：保留概念，不做 Role 编辑器

用户语言使用：

```text
重要游览地
```

例如：

```text
蒂阿瑙  ♡ 想去
  Milford Sound
  重要游览地 · ⭐ 必去 · 预计全天
```

用户不看到：

```text
planningRole=core_visit
parent candidate
Detail → Core
Core → Detail
```

如果用户觉得它不该占这么多时间，可在“更多”中提供自然操作：

```text
不需要单独安排这么多时间
```

如果用户说：

```text
这个地方很重要，单独留一天
```

系统内部可以把普通兴趣点升级为重要游览地，并在必要时展示影响确认。

Step 4 不提供第二套重要游览地编辑器。

---

# 11. Step 2 地图

显示：

```text
停留区域
重要游览地
```

不显示大量普通 Detail Interest。

地图点击只：

```text
选中对象
→ 右侧显示对应详情
```

Popup 不提供删除、偏好、角色、定位修复、生成路线等业务操作。

---

# 12. Step 3：路线和天数

用户任务：

> 根据总天数，把真正排得下的地点变成最终路线。

这是 Step 2 与 Step 3 的清晰分工：

```text
Step 2：我想考虑哪些地方
Step 3：这些地方里，最终怎么排
```

## 没有路线

```text
[生成路线和天数]
```

## 需要重新确认

```text
[更新路线和天数]
```

## 已确认

```text
[下一步：补充景点]
```

---

# 13. Step 3 主视觉：时间轴 / 停留段

推荐：

```text
Day 1–2
奥克兰 · 2 天

↓ 自驾

Day 3–4
罗托鲁瓦 · 2 天

↓ 自驾

Day 5
陶波 · 1 天
```

环线：

```text
Day 1–2   奥克兰
...
Day 19–20 奥克兰
```

两个奥克兰是两段独立停留。

UI 不显示 `stayBlockId`。

---

# 14. Step 3 “采用 / 未采用”使用渐进披露

`must_go` 停留区域一定进入路线。

`want_to_go` 如果没有进入，必须解释。

但页面不要铺满所有 optional 未采用候选。

默认：

```text
路线已安排 8 个停留地点
还有 2 个“想去”的地方没有排进路线

[查看原因]
```

展开后：

```text
Napier · 想去
未纳入：会明显增加绕行

Waitomo · 想去
未纳入：当前天数不足
```

普通 optional 未采用候选收在更次级的：

```text
其他未采用候选（5）
```

---

# 15. Step 3 手工编辑：用户只看到“还差几天”

选中停留段后允许：

```text
调整停留天数
调整顺序
调整进入该段的交通方式
```

内部使用 Draft，但 UI 不显示 Draft / Apply / canonical 术语。

例如：

```text
皇后镇 4 → 3 天

总旅行：20 天
当前分配：19 天
还剩 1 天需要安排
```

建议直接给出：

```text
[+1 蒂阿瑙]
[+1 瓦纳卡]
[让我帮你安排]
```

此时：

```text
[保存调整] disabled
```

当分配恢复完整后：

```text
总旅行：20 天
当前分配：20 天
✓ 已分配完整

[保存调整]
```

---

# 16. Step 3 自然语言编辑

用户说：

```text
皇后镇少一天
```

如果系统不知道这一天下放到哪里：

```text
不要静默决定
```

应该直接给建议：

```text
皇后镇减少 1 天后，还需要重新安排 1 天。

建议：
[加到蒂阿瑙]
[加到瓦纳卡]
[让我合理安排]
```

除非用户明确授权“你合理分配”，AI 才完整决定。

---

# 17. 移动日统一说明

UI 始终使用：

> **移动到某个区域的当天，算作到达区域的第 1 天。**

例如：

```text
A 2 天
B 3 天

Day 1 A
Day 2 A
Day 3 A → B  // B 第 1 天
Day 4 B
Day 5 B
```

所有页面不得出现另一种计数口径。

---

# 18. Step 3 更新完成后的 Diff

默认简洁：

```text
路线已更新
蒂阿瑙：2 → 3 天
皇后镇：4 → 3 天
其他 15 天不变
```

不展示内部 Day ID / fingerprint / affectedDayIds。

如果结构实际未变化：

```text
路线和停留天数无需调整。
只需要更新蒂阿瑙的每日安排。
```

---

# 19. 未定位提示：非阻塞轻量，阻塞才突出

Planning Area 尚未定位但仍能做 Step 3 时：

```text
尚未定位 · 真实路线稍后计算
```

不要用大红色阻塞卡。

只有真正影响下一步时才突出：

```text
Day 12 的起点 / 终点还没有定位
需要先完成定位才能生成真实每日路线

[去定位]
```

普通 want / optional 兴趣点未定位时只用轻量状态，不阻塞其他内容。

---

# 20. Step 4：补充景点（可选）

用户任务：

> 路线已经确定，要不要再找一些值得加入的普通景点？

Step 4 明确是可选增强步骤。

第一次进入：

```text
只展示已有内容
不自动生成
```

默认 Primary：

```text
[下一步：每日行程]
```

Secondary：

```text
[帮我补充景点]
```

如果用户已有足够地点，可以直接跳过。

如果用户主动点击“帮我补充景点”，AI 只针对已进入路线的停留区域按容量推荐。

每个区域可返回 0–9 个，允许 0。

---

# 21. Step 4 内容结构

```text
蒂阿瑙 · 2 天

重要游览地
★ Milford Sound · 必去 · 预计全天

普通兴趣点
Glowworm Caves
Lake Te Anau
```

重要游览地在 Step 4 只作为时间背景。

点击后允许查看摘要，但不要出现第二套角色 / parent 编辑 UI。

普通兴趣点可以：

```text
设为必去
设为想去
移除 / 不考虑
定位
```

高级“需要单独安排很多时间”通过自然语言或更多菜单进入 Step 2 归属逻辑。

---

# 22. Step 4 上游需要更新时

如果路线 / 天数已经过期：

仍允许：

```text
浏览
手工新增
编辑
定位
设置必去 / 想去
```

但不能基于旧容量继续 AI 批量推荐。

默认紧凑提示：

```text
路线和天数需要重新确认
补充推荐暂时不可用

[去更新]
```

点击后自动切换 Step 3。

---

# 23. Step 5：每日行程

## 没有每日行程

```text
[生成每日行程]
```

## 局部需要更新

```text
[更新受影响的 2 天]
```

## 路线和天数需要更新

```text
路线和天数需要重新确认
[去更新]
```

点击后自动切换 Step 3，并保留用户当前上下文。

---

# 24. Step 5 日列表与局部状态

```text
Day 12 蒂阿瑙  已完成
Day 13 蒂阿瑙  需更新
Day 14 皇后镇  已完成
```

汇总：

```text
2 天需更新
其他 18 天不变
```

默认不要显示：

```text
重新生成全部 20 天
```

全量重做只作为 Secondary / Danger。

---

# 25. Detailed Update 最小变更体验

更新时用户应感受到：

```text
只改需要改的天
我手工调整过的内容尽量保留
没有关系的日程不被重做
```

系统内部：

```text
affectedDayIds
sticky baseline
minimal diff
```

UI 不显示这些术语。

如果必须大改某一天：

```text
先显示简洁 Diff
```

例如：

```text
Day 13 调整较大
- 新增 Milford Sound
- Glowworm Caves 移到 Day 12
- 出发时间 09:00 → 07:30

[确认更新]
```

---

# 26. Update Card：默认紧凑，按需展开

系统内部仍必须知道完整影响：

```text
为什么
影响哪些区域 / Day
哪些内容不变
下一步是什么
```

默认只显示：

```text
⚠ 蒂阿瑙的安排需要更新
预计影响 2 天，其他 18 天不变

[去更新] [查看原因]
```

点“查看原因”才展开：

```text
Milford Sound 已被设为重要游览地，原来的 2 天没有考虑这个全天活动……
```

禁止默认把每次变更都做成长篇 Impact Card。

---

# 27. 删除确认也要按影响分级

普通未使用兴趣点：

```text
轻量删除 + Undo
```

高影响删除：

```text
删除“蒂阿瑙”会同时影响：
- Milford Sound（必去）
- 2 个普通景点
- Day 12–13

[取消] [确认删除]
```

默认只展示关键影响；详细清单可展开。

不能静默 cascade。

自然语言删除遵守同样规则。

---

# 28. AI Composer

AI Composer 是右侧控制台的一部分，不是第二套管理系统。

用户可以说：

```text
Milford 我一定要去
皇后镇少一天
这个地方不用专门留一天
给蒂阿瑙再找两个值得去的地方
```

系统自动定位到正确步骤和对象。

高影响动作必须说明关键结果并确认，但不需要向用户解释：

```text
WorkflowStep
Action Registry
Scope
CAS
```

---

# 29. 不自动发生的事

进入页面不得自动：

```text
批量生成兴趣点
重新规划路线和天数
重新生成每日行程
角色升级 / 降级
大范围删除
改变用户偏好
```

可以自动：

```text
读取
恢复选中对象
只读依赖分析
展示简洁 Diff
新地点保存后的 best-effort 定位
Provider 路线刷新
自动切换到正确工作步骤
```

自动切换步骤不等于自动执行 mutation。

---

# 30. 移动端

窄屏：

```text
主视图 = 工作区全屏
地图 = Tab / 抽屉
```

地图仍只展示 / 选择，不创造第二套编辑入口。

五步导航继续保留，但 Step 4 标明：

```text
可选
```

# 31. 核心验收：简单用户不需要学系统术语

第一次使用的用户，不理解任何内部名词，也应能完成：

```text
旅行需求
→ 想去哪些地方
→ 路线和天数
→ 可选地补充景点
→ 每日行程
```

验收时禁止依赖用户理解：

```text
Core Visit
Macro
Skeleton
PlanningRole
Fingerprint
Dirty
Resolution
```

---

# 32. 核心验收：复杂功能隐藏在背后

必须满足：

```text
Step 2 看起来是愿望清单，而不是 Schema 编辑器
Step 3 能解释为什么某个“想去”地点没排进去
四级 preference 不变成四按钮系统
重要游览地不变成 Role 管理器
Step 3 分配不合法时只告诉用户“还差几天”
Step 4 可以直接跳过
Update Card 默认短，原因可展开
跨步骤请求自动切换上下文
未定位只在真正阻塞时突出
地图不承担业务 mutation
```

---

# 33. 最终 UX 心智

用户：

```text
我想怎么玩
→ 我想去哪些地方
→ 这些天怎么排
→ 要不要再补点景点
→ 每天具体怎么玩
```

系统内部：

```text
Candidate-first
PlanningRole
Stay Block
Macro fingerprint
Impact Analyzer
affectedDayIds
Resolution
CAS
```

但用户不需要知道这些。

最终体验应该是：

> **用户只是在自然地规划旅行；复杂依赖、状态管理和增量更新全部由系统在背后处理。**
