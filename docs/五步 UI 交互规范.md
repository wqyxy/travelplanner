# TravelPlanner 五步 UI 交互规范

## 1. 文档目的

本文档定义 TravelPlanner 五步规划流程的用户交互边界。

目标不是描述底层数据结构，而是确保用户始终知道：

```text
我现在在哪一步？
这一页主要要做什么？
哪些地方可以修改？
修改后会影响什么？
下一步应该点哪里？
```

本规范与《TravelPlanner 五步规划流程重构实施方案》配套。

如果底层能力与本规范发生冲突，优先遵守以下产品原则：

> 同一类操作只能有一个明确主入口；地图负责展示和选择，右侧工作区负责修改和确认；系统修改上游规划后，只更新真正受影响的部分。

---

# 2. 五步用户导航

用户可见名称统一使用：

```text
1 旅行需求
2 去哪些地方
3 安排路线和天数
4 补充景点
5 每日行程
```

不要在主导航直接使用：

```text
Backbone
Skeleton
Macro
Detail
Planning Area
Core Visit
```

这些可以存在于内部模型、代码和调试信息中，但不是用户完成任务的前置知识。

---

# 3. 页面总体布局原则

建议长期保持三块区域：

```text
左侧：五步导航 / 当前步骤状态
中间：地图 / 路线 / 可视化结果
右侧：当前步骤唯一主工作区
```

其中：

## 左侧

负责：

```text
步骤导航
步骤状态
是否需更新
是否存在阻塞
```

不承担复杂编辑。

## 中间地图

负责：

```text
展示
聚焦
选择
路线可视化
```

地图可以触发 selection，但不能直接形成第二套完整编辑系统。

## 右侧工作区

负责：

```text
查看当前对象详情
新增
删除
修改
设置优先级
设置角色
确认影响
启动 AI 动作
继续到下一步
```

所有主要交互必须汇聚到这里。

---

# 4. 唯一入口原则

这是整个 UI 最重要的规则。

同一个业务动作不能同时存在：

```text
地图右键一套
地图弹窗一套
列表一套
聊天一套
详情页一套
```

如果一个对象可以编辑，唯一主入口必须在右侧工作区。

地图点击对象后：

```text
地图对象被选中
→ 更新 selection
→ 右侧切换到对应对象详情
```

用户继续在右侧完成修改。

聊天可以提出和识别用户意图，但任何会改变 canonical 旅行数据的高影响操作仍应通过右侧 Action Card / 确认区完成。

---

# 5. 选择模型

整个 App 只维护一个主要 `selection`。

可选择对象包括：

```text
Planning Area
Core Visit
Detail Interest
Day
Stop
Route Segment
```

点击地图、列表、时间轴，本质上都只是更新同一 selection。

禁止不同组件各自维护“当前编辑对象”。

---

# 6. Step 1：旅行需求

用户任务：

> 告诉系统我想进行什么样的旅行。

右侧工作区主要显示：

```text
日期 / 天数
出发地
旅行人数
交通方式
节奏
主题 / 偏好
明确限制
用户明确想去的地方
```

主操作：

```text
生成推荐地点
```

如果已有 Step 2 数据，再次修改 Step 1 后：

- 若不影响 Macro Dependency，不标记后续过期；
- 若影响路线、停留时间或核心规划，则 Step 3 进入 `needs_update`；
- 只标记真正受影响的后续部分。

Step 1 页面不要直接出现“生成每日行程”等跨层动作。

---

# 7. Step 2：去哪些地方

用户任务：

> 确认这趟旅行围绕哪些停留城市 / 区域和重要游览地展开。

## 7.1 右侧结构

建议分为：

```text
停留城市 / 区域
重要游览地
```

用户文案：

```text
停留城市 / 区域
= 你会在这里住宿、停留或组织路线

重要游览地
= 会占用较多时间、明显绕行，或需要单独安排半天 / 一天的地方
```

不要要求用户理解 `planning_area` 和 `core_visit` 才能操作。

## 7.2 列表表现

推荐：

```text
蒂阿瑙
  Milford Sound           [核心]

皇后镇
  Routeburn Track         [核心]
```

可以显示 preference：

```text
必去
想去
可选
```

但不要把 `核心` 和 `必去` 混成一个状态。

## 7.3 主操作

首次：

```text
生成推荐地点
```

已有结果后主操作：

```text
安排路线和天数
```

如果 Skeleton 已存在且 `macroDirty = true`：

```text
更新路线和天数
```

## 7.4 新增

新增按钮打开：

```text
添加停留城市 / 区域
添加重要游览地
```

添加重要游览地时必须明确其所属停留区域。

## 7.5 地图

显示：

```text
停留城市 / 区域
重要游览地
```

不显示大量普通兴趣点。

Core Visit marker 可区别于 Planning Area，但不可被误画为 Macro Route 中间站。

---

# 8. Step 3：安排路线和天数

用户任务：

> 决定去的顺序，以及每个地方分多少天。

这是五步流程中最重要的结构确认步骤。

## 8.1 主视觉必须是时间轴

不能只显示普通列表。

推荐：

```text
Day 1–2
奥克兰 · 2 天

↓ 自驾

Day 3–4
罗托鲁瓦 · 2 天

↓ 自驾

Day 5
陶波 · 1 天
```

用户应该一眼理解：

> 这是在切分我的总旅行天数。

## 8.2 右侧详情

选中某个区域后显示：

```text
区域名称
停留天数
进入方式
离开方式
影响时间分配的重要游览地
为什么安排这么多天
```

Core Visit 在这里仅作为“时间容量原因”展示。

不要让用户误以为第三步已经决定具体哪一天去 Milford Sound。

## 8.3 主操作

无 Skeleton：

```text
生成路线和天数
```

已有 Skeleton 且 Dirty：

```text
更新路线和天数
```

Ready：

```text
继续补充景点
```

## 8.4 更新后的结果必须解释 Diff

例如：

```text
蒂阿瑙：2 天 → 3 天
皇后镇：4 天 → 3 天
其他 15 天保持不变
```

如果重新规划后结构完全相同：

```text
路线和停留天数无需调整。
只需要更新蒂阿瑙的每日安排。
```

禁止只显示“更新完成”。

## 8.5 地图

显示 Macro Route：

```text
Planning Area → Planning Area
```

Core Visit 不进入 Macro Route。

---

# 9. Step 4：补充景点

用户任务：

> 在已经确定的时间容量里，为每个区域补充普通景点和活动。

## 9.1 首次进入不要自动批量生成

首次进入只显示已有内容。

主操作：

```text
根据当前行程补充兴趣点
```

只有用户点击后才启动 AI Discovery。

## 9.2 分区结构

按 Planning Area 分组：

```text
蒂阿瑙 · 2 天

重要游览地
★ Milford Sound

普通兴趣点
○ Glowworm Caves
○ Lake Te Anau
○ Bird Sanctuary
```

Core Visit 在 Step 4 继续可见。

原因：用户需要知道为什么当前区域剩余时间有限。

## 9.3 普通兴趣点操作

允许：

```text
新增
删除
替换
修改 preference
定位
设为重要游览地
```

默认新增为普通兴趣点。

“设为重要游览地”是显式高影响操作。

操作后系统必须提示：

```text
这个地点现在会参与路线和停留天数判断。
需要重新检查“安排路线和天数”。
```

## 9.4 Skeleton Dirty 状态

如果上游 Macro Dirty：

允许继续：

```text
浏览
手工新增
编辑
定位
调整 preference
```

禁止：

```text
根据旧 stayDays 继续自动批量发现兴趣点
```

右侧固定提示：

```text
路线或停留天数可能已经变化。
先更新路线和天数，再继续按容量补充景点。

[更新路线和天数]
```

主按钮必须替换成“更新路线和天数”。

---

# 10. Step 5：每日行程

用户任务：

> 确认每天具体几点去哪里，以及当天的真实路线。

## 10.1 日列表

推荐：

```text
Day 12  蒂阿瑙        Ready
Day 13  蒂阿瑙        需更新
Day 14  皇后镇        Ready
```

若只有局部受影响，必须直接显示：

```text
2 天需更新
其他 18 天保持不变
```

## 10.2 单日详情

选中 Day 后：

```text
起点
Stop 列表
时间
交通方式
终点
Detail Route
```

Core Visit 与普通兴趣点都作为 Stop 展示，不作为 Macro Anchor。

## 10.3 主操作

无详细行程：

```text
生成每日行程
```

局部 Dirty：

```text
更新受影响的 2 天
```

不要默认显示：

```text
重新生成全部 20 天
```

全量重做只能作为次级危险操作。

## 10.4 上游 Macro Dirty

如果 Step 3 尚未更新：

禁止新的 Detailed Generate / Update。

主提示：

```text
路线和停留天数尚未确认。
先更新 Step 3，避免按旧结构重新安排每日路线。

[更新路线和天数]
```

---

# 11. “需更新”统一交互规范

任何 `needs_update / needs_review / macroDirty` 不得只是一个图标或状态词。

必须形成统一 Update Card：

```text
为什么需要更新
受影响的区域 / Day
不受影响的内容
唯一主操作
```

例如：

```text
Milford Sound 已设为重要游览地。
原来的蒂阿瑙 2 天规划没有考虑这个全天活动。

可能影响：
- 蒂阿瑙
- 与蒂阿瑙相邻的移动日

保持不变：
- 其他 18 天

[更新路线和天数]
```

禁止笼统显示：

```text
行程已过期
请重新生成
```

---

# 12. 未定位状态

未定位地点不应等到 Step 5 失败时才第一次出现。

从 Step 2 / Step 4 起就显示：

```text
⚠ 尚未定位
```

点开详情：

```text
不会影响当前路线和天数规划，
但生成实际每日路线前需要完成定位。

[重新定位]
[手工定位]
```

如果 `must_go + unresolved`：

Step 5 顶部直接显示阻塞原因。

不要只在 Action 执行失败后用 Toast 报错。

---

# 13. 删除确认规范

普通未使用兴趣点删除可以轻量确认或直接撤销式删除。

高影响删除必须进入 Impact Confirmation Card。

例如删除蒂阿瑙：

```text
删除“蒂阿瑙”还会删除：

重要游览地
- Milford Sound [必去]

普通兴趣点
- Glowworm Caves
- Lake Te Anau

受影响行程
- Day 12
- Day 13

[取消] [确认删除]
```

禁止静默级联。

自然语言删除同样遵守此规则。

---

# 14. AI 对话与右侧工作区的关系

AI 对话是“意图入口”，不是第二套数据管理 UI。

用户可以说：

```text
Milford 我一定要去
把皇后镇减少一天
这个景点设为重要地点
```

AI 识别后：

低风险、无歧义动作可直接生成 Action Card。

高影响动作必须在右侧展示：

```text
将修改什么
为什么
影响哪些步骤 / Day
确认按钮
```

禁止 AI 在聊天区静默完成会大范围改变规划的数据修改。

---

# 15. 主按钮优先级

右侧工作区每个时刻最多一个 Primary Button。

优先级：

```text
1 阻塞修复
2 上游更新
3 当前步骤生成 / 更新
4 继续下一步
```

例如：

如果 Step 4 当前 Skeleton Dirty：

Primary：

```text
更新路线和天数
```

而不是同时出现：

```text
补充兴趣点
继续每日行程
更新路线
重新生成
```

其他动作都降为 Secondary / Menu。

---

# 16. 状态文案规范

用户可见状态尽量使用：

```text
已完成
需更新
未开始
处理中
需要处理
```

避免直接显示：

```text
macroDirty
needs_review
stale
invalid
```

用户点击状态可展开工程原因，但默认展示产品语言。

---

# 17. 不自动做的事情

以下动作禁止因为“进入页面”而自动发生：

```text
批量生成大量兴趣点
重新生成行程骨架
重新生成每日行程
大范围删除
角色升级 / 降级
自动改变用户 preference
```

进入页面可以自动：

```text
读取
聚焦
计算只读状态
展示 diff
展示未定位提示
```

---

# 18. 可以自动做的后台动作

不改变用户规划意图、且属于 best-effort 基础设施的动作可以自动：

```text
新地点保存后尝试地图定位
路线 Provider 刷新
只读影响分析
状态计算
地图 marker 更新
```

失败不得导致用户刚确认的数据消失。

---

# 19. 增量修改体验示例

## 示例 A：新增一个普通咖啡馆

结果：

```text
Step 3 不变
Step 5 不变
只是新增候选
```

UI 不提示整趟行程需更新。

## 示例 B：咖啡馆改为“必去”

如果已存在可承载 Day：

```text
只标记对应区域 Day 需更新
```

## 示例 C：普通景点升级为重要游览地

```text
Step 3 需更新
对应区域的 Detailed Day 需检查
其他地区保持不变
```

## 示例 D：Step 3 重算后 Macro 完全相同

```text
Step 3 恢复已完成
只更新该区域 Detailed Day
```

## 示例 E：Step 3 天数发生变化

例如：

```text
Te Anau 2 → 3
Queenstown 4 → 3
```

只将真正涉及的 Day 标记为需更新。

# 20. 地图交互细则

地图点击：

```text
只选中对象
```

地图 marker popup 可提供：

```text
名称
类型
状态
查看详情
```

“查看详情”只是把右侧工作区切换到对应对象。

不要在 popup 中堆叠：

```text
删除
换地点
设置必去
设为核心
编辑时间
重新生成路线
```

否则地图会重新变成第二套操作入口。

---

# 21. 移动端 / 窄屏原则

如果无法同时展示地图和右侧工作区：

优先保留“工作区为主、地图为辅”。

推荐：

```text
主视图：当前步骤工作区
地图：底部抽屉 / Tab
```

仍然保持：

```text
地图只负责选择
编辑回到工作区
```

# 22. 验收标准

## 22.1 第一次规划

用户不需要理解内部术语，也能完成：

```text
需求
→ 去哪些地方
→ 分配路线和天数
→ 补充景点
→ 每日行程
```

## 22.2 修改体验

任何局部修改后，用户都能看到：

```text
为什么需要更新
影响哪些内容
哪些内容不变
下一步唯一应该做什么
```

## 22.3 唯一入口

同一个对象的增删改不存在两套并行主入口。

地图不承担完整编辑。

## 22.4 自动生成

进入 Step 4 不自动生成大量兴趣点。

进入 Step 5 不自动重新生成所有行程。

## 22.5 局部更新

新增普通 optional 兴趣点不会让整个行程失效。

Core Visit 变化不会直接让整趟 Detailed Itinerary 全部失效。

## 22.6 未定位

用户在 Step 5 前已经知道哪些重要地点仍未定位。

---

# 23. 最终 UX 原则

用户最终应形成非常稳定的心智模型：

```text
我要怎么玩
→ 去哪些地方
→ 这些天怎么分
→ 还有什么值得去
→ 每天具体怎么玩
```

系统的行为则遵循：

```text
上游决定结构
下游补充细节
局部修改只局部失效
地图只展示和选择
右侧工作区是唯一主编辑入口
任何“需更新”都解释原因和影响范围
```

最终体验不应该像“AI 一次性生成一份攻略”，而应该像一个持续可修改、知道依赖关系的旅行规划工作台。
