# TravelPlanner 产品文档

> 状态：**当前产品现状**  
> 更新日期：2026-09-05

---

# 1. 产品结构

当前产品只有两个正常工作区：

```text
规划 · 旅行需求
行程 · 最终线路
```

用户真正维护的旅行路线只有一份：**最终线路**。

```text
旅行需求
→ 最终线路
→ 自动得到 Day
→ 自动得到地图路线
```

旧的 Candidate、Skeleton、独立“补充景点”、独立 Day/Stop 页面不再是用户工作流。

---

# 2. 旅行需求

“规划 · 旅行需求”负责整趟旅行的基础条件，例如：

- 目的地 / 出发地；
- 日期 / 天数；
- 人数；
- 交通偏好；
- 节奏、主题、兴趣；
- 预算与限制；
- 其他自然语言要求。

需求可以不完整。系统可以提醒，但不会因为旅行经验上“不够合理”而擅自修改用户线路。

---

# 3. 最终线路

“行程 · 最终线路”是主要规划区。

每个线路节点表示某个现实 Place 在线路中的一次出现：

```text
id
placeId
status
endsDay
transportFromPrevious
详细安排字段
```

同一个 Place 可以出现多次，每次拥有独立 route node ID。

例如：

```text
A
→ 陶波 #1【住】
→ 陶波 #2【住】
→ B
```

---

# 4. 右侧是唯一线路业务入口

用户在右侧最终线路区域完成：

- 手工添加地点；
- 删除某一次线路出现；
- 拖动 / 上移 / 下移；
- 正常 / 待定 / 不去；
- 住 / 不住 / 多一晚；
- 到达当前地点的交通方式；
- 详细安排；
- 地点名称 / 类型编辑；
- 重新识别、Google Maps 链接、地图选点；
- AI 生成主要地点；
- AI 生成详细地点；
- AI 完善某一天；
- AI 优化一天 / 一段 / 全程；
- AI 方案的采用 / 不采用 / 撤销。

地图不提供第二套删除、状态、住宿或优化按钮。

---

# 5. 节点状态

```text
normal     正常
tentative  待定
no_go      不去
```

`tentative / no_go`：

- 仍保留在线路原位置；
- 已定位时仍显示在地图；
- 原 `endsDay` 和到达交通继续保存；
- 暂时退出当前 Day 和交通路线；
- 恢复 normal 后原位置和原设置重新生效。

只有“从线路移除”才真正删除这一次线路节点。

---

# 6. 住 / 不住 / 多一晚

`住`：

```text
endsDay = true
```

`不住` 只取消该分界，不删除、不移动其他地点，也不自动寻找替代住宿点。

`多一晚` 会在当前节点后新增一个引用同一 Place 的独立 route node。

系统不要求用户维护 `stayDays=2` 这样的第二套住宿逻辑。

---

# 7. Day 自动派生

Day 不作为第二份独立线路维护。

```text
旅行起点
+ normal route nodes
+ 当前生效的 endsDay
→ Day 1 / Day 2 / ...
```

顺序、状态、住宿分界变化后，Day 编号和日期自动重新计算。

最后一个 normal 节点即使没有 `endsDay=true` 也能形成合法最后一天。

---

# 8. 到达交通与 Provider 事实

交通属于“到达当前节点”。

```text
A —drive→ X —walk→ B
```

X inactive 后：

```text
A —walk→ B
```

恢复 X 后仍是：

```text
A —drive→ X —walk→ B
```

最终线路只保存用户选择的交通 mode。

真实：

- 距离；
- 时长；
- geometry；

只能来自 Route Provider，不能由 AI、UI 或 API 调用方伪造。

---

# 9. 详细安排仍属于最终线路

旧 Step 5 不再存在，但“活动 / 时间 / 备注”能力保留在线路节点上。

用户选择一个当天中途地点后，可以直接在右侧填写：

- 活动说明；
- 上午 / 下午 / 傍晚 / 夜间 / 全天；
- 开始时间；
- 结束时间；
- 预计停留分钟；
- 备注。

如果已有自然语言 `scheduleText`，右侧会直接展示。

这些修改只更新当前线路节点的详细安排，不改变：

- 地点顺序；
- status；
- 住宿分界；
- Place 身份；
- Provider 路线事实。

当天结束节点继续承担 Day boundary 角色，不作为当天中途 Stop 单独维护时间表。

---

# 10. AI：生成主要地点

最终线路为空时，用户可以点击：

```text
生成主要地点
```

AI 研究整趟旅行最重要的地点，结果直接进入最终线路，不再进入独立候选页面。

AI 可以对**本轮新增节点**建议：

- 顺序；
- 是否作为一天结束位置；
- 到达交通 mode。

没有“每个生成地点默认住一晚”的规则。

AI 不确定住宿分界时，可以全部返回 `endsDay=false`。

已经存在最终线路后，普通“生成主要地点”不能覆盖用户线路。

同一现实 Place 可以在 AI 主线路中出现多次，每次形成独立 route node。

---

# 11. AI：生成详细地点

最终线路存在后，用户可以：

```text
生成全程详细地点
补充某一天的详细地点
补充指定连续线路段的详细地点
```

详细地点可以是景点、观景点、活动、餐厅或其他真实旅行地点。

普通详细地点生成只有一个线路权限：**插入新节点**。

它不能：

- 重排已有节点；
- 删除已有节点；
- 改变已有 status；
- 改变已有 `endsDay`；
- 修改已有到达交通；
- 把已有节点移动到其他 Day。

局部 Day / segment scope 找不到合法锚点时会直接拒绝，不会偷偷把新地点插到范围外。

---

# 12. AI：完善这一天

每个有中途地点的 Day 可以点击：

```text
完善这一天
```

AI 只为当前已有地点补：

- activity；
- period；
- scheduleText；
- start / end time；
- duration；
- notes。

它不能：

- 新增 / 删除 / 替换地点；
- 改顺序；
- 改状态；
- 改住宿分界；
- 改已有交通事实；
- 把 verification 从未核验伪装成已核验。

结果先形成方案，用户决定是否采用。

---

# 13. AI：显式优化

只有用户明确点击优化时，AI 才获得重排已有节点的权限：

```text
优化这一天
优化这一段
优化全程
```

服务器会明确计算本轮授权 route-node ID 集合。

AI 必须恰好返回这些已有 ID 的新顺序，不能新增、删除、重复或伪造节点。

`tentative / no_go` 不属于可移动集合，保持原线路槽位。

单日优化只移动当天 Stop；当天结束 boundary 固定不动。

优化完成后先形成 Proposal：

```text
采用这个方案
不采用
```

采用后，如果没有后续冲突修改，还可以撤销。

---

# 14. 地图

地图负责：

- 显示所有已定位 route nodes；
- 显示 normal 节点形成的当前路线；
- 选择 / 聚焦地点；
- 辅助人工定位。

normal / tentative / no_go 使用不同视觉状态。

如果节点变成 inactive，已经不符合当前 Day 的旧 dirty Provider geometry 不会继续穿过该节点显示。

路线重算失败不会回滚已经保存的最终线路。

---

# 15. 未定位地点

Provider 暂时找不到地点时：

- 地点继续保留；
- 不自动删除；
- 不自动补位；
- 不导致整条线路失败；
- 可以重新识别；
- 可以粘贴 Google Maps 链接；
- 可以从右侧进入地图选点。

系统不能为了显示地图而伪造坐标。

---

# 16. 用户控制原则

> **用户是旅行方案的唯一决策者，AI 只提供研究、提醒和可撤销建议。**

系统可以提醒不合理、冲突、未定位或路线待更新，但不能因为这些问题擅自重排、删除或改住宿。

应该硬失败的主要是：

- 数据结构损坏；
- 实体引用无效；
- Scope / AI 权限越界；
- generation / Revision 并发冲突；
- 非法 Schema；
- 安全边界；
- 伪造 Provider 事实。

---

# 17. 已退出正常用户路径的旧职责

下面这些概念可能仍作为内部兼容结构存在，但用户不再维护：

- 独立 Candidate 页面；
- 独立 Skeleton / stayDays 页面；
- 独立“补充景点”步骤；
- 独立 Step 5 Day / Stop 页面；
- 五步导航。

它们不能成为 finalRoute 之外的第二份用户线路来源。
