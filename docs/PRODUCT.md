# TravelPlanner 产品文档

> 状态：**当前产品现状**  
> 更新日期：2026-09-05  
> 本文件只描述当前 `main` 上用户实际面对的产品结构和行为，不描述下一版目标。  
> 下一步改造目标见 [`PLAN.md`](./PLAN.md)。

---

# 1. 当前产品定位

TravelPlanner 当前是一个以 **地图 / 行程展示 + 右侧控制台 + 五步规划流程** 为核心的 AI 旅行规划工作台。

当前产品不是一次性生成攻略，而是让用户逐步形成：

```text
旅行需求
→ 候选地点
→ 路线和停留天数
→ 补充普通景点
→ 每日详细行程
```

产品已经采用“用户决定、AI 辅助”的原则：系统可以给出规划提醒，但普通的旅行合理性问题不应成为用户保存手工方案的硬阻塞。

地图 Provider 负责真实坐标、地点 ID、路线 geometry、距离和时长等事实；AI 不负责伪造这些 Provider 事实。

---

# 2. 当前用户流程：五步

当前界面明确显示五个步骤：

```text
1 旅行需求
2 想去哪些地方
3 路线和天数
4 补充景点（可选）
5 每日行程
```

这五步目前分别拥有独立的产品职责和独立页面状态。

用户可以在五步之间进入和编辑；系统通过提醒和更新状态告诉用户哪些后续内容可能需要重新确认。

---

# 3. Step 1：旅行需求

当前 Step 1 负责整趟旅行的基础输入，例如：

```text
目的地 / 出发地
日期 / 天数
人数
交通偏好
旅行节奏
主题与兴趣
预算和限制
其他自然语言要求
```

这些信息是后续地点发现和行程生成的输入。

修改需求后，系统会判断是否影响后面的宏观路线或每日行程；真正受影响的内容可以显示“需要更新”或 Advisory，而不是强制用户从头重做全部步骤。

---

# 4. Step 2：想去哪些地方

当前 Step 2 是独立的 **Candidate 候选地点池**。

当前候选地点内部可以区分：

```text
Planning Area
Core Visit
Detail Interest
```

Step 2 主要展示和生成：

```text
Planning Area
Core Visit
```

用户可以：

```text
AI 生成地点
手动新增
编辑
移除
修改偏好
处理定位
```

当前 Candidate 偏好数据仍为：

```text
must_go
want_to_go
optional
excluded
```

这些偏好会参与后续规划，但当前系统已经允许用户保留“不典型”或 AI 不建议的方案，不因为启发式不合理而强制删除。

Step 2 中的 Candidate 还不是最终的每日线路 Stop。

---

# 5. Step 3：路线和天数

当前 Step 3 使用 **Stay Block / Skeleton** 思路设计宏观行程。

每一段停留主要表达：

```text
Planning Area
stayDays
从上一段到这里的交通方式
```

当前用户可以：

```text
调整停留区域顺序
修改 stayDays
修改跨区域交通方式
把停留区域加入 / 移出当前 Skeleton
保存宏观路线调整
```

系统再把这些 Stay Block 展开成实际 Day。

例如：

```text
A：2 天
B：3 天
```

会形成多天 Day；每个 Day 有起点和终点，但 Step 3 本身不负责普通景点级 Stop 的详细安排。

当前 Step 3 的手工规划不再要求“旅行天数一定完美匹配”才能作为旅行方案存在；不完整、超额或不合理的规划可以通过 Advisory 提醒用户，而不是由系统擅自修正。

---

# 6. Step 4：补充景点（可选）

当前 Step 4 是独立的普通兴趣点补充页面。

主要处理：

```text
Detail Interest
景点
餐厅
观景点
普通活动
```

用户可以浏览已有兴趣点、手动增加，也可以让 AI 根据当前停留区域和旅行节奏补充推荐。

Step 4 当前仍然是 **Candidate 层**：

> 新增一个景点，不等于这个景点已经被安排进某一天的真实线路。

也就是说，Step 4 和 Step 5 之间仍存在“候选地点 → 每日 Stop”的第二次安排过程。

---

# 7. Step 5：每日行程

当前 Step 5 才是实际的 Day / Stop 级详细行程。

每个 Day 当前包含：

```text
Day 编号 / 日期 / 标题
起点 Anchor
多个 Stops
终点 Anchor
日内交通信息
详细程度和需确认状态
```

AI 的详细行程生成 / 更新会根据当前 Step 3 路线、Candidate 和用户偏好，把具体地点安排进对应 Day 的 Stop 序列。

用户可以围绕某一天：

```text
生成详细行程
更新受影响的天
调整 Stop
移动 Stop
修改 Anchor
优化某一天
重新计算路线
```

当前产品会尽量只更新真正受影响的 Day，避免无关日程被全部重做。

---

# 8. 当前地图与路线体验

页面当前保持：

```text
地图 / 行程展示
+
右侧控制区域
```

地图主要负责：

```text
显示地点
显示路线
选中 / 聚焦对象
辅助定位
```

业务编辑主要通过右侧工作区完成。

当前真实日内路线按：

```text
Day 起点
→ Day Stops
→ Day 终点
```

计算。

跨区域宏观路线和日内详细路线当前仍是两个层次的路线状态。

地点可以先保存、后定位。未定位不会导致地点本身被自动删除；但 Provider 无法提供真实路线事实时，系统只能显示待定位 / attention 状态，不能伪造距离、时长或 geometry。

---

# 9. 当前“地点”和“行程”是多层结构

当前产品里，同一个旅行地点可能先后经历不同层次：

```text
Place
→ Candidate
→ Planning Area / Core Visit / Detail Interest
→ Skeleton / Stay Block
→ Day Anchor / Day Stop
→ Route
```

因此当前产品实际存在几份互相关联、需要保持一致的内容：

```text
Candidate 候选池
Step 3 Skeleton
Day 列表
Day Stops
地图定位
Macro / Detail Route
```

系统通过 dependency / update state 尽量保证局部更新，而不是要求用户自己理解这些内部结构。

---

# 10. 当前用户控制原则

当前产品已经明确：

> **用户保存的旅行方案优先于系统的“合理性判断”。**

系统可以提醒：

```text
日期不匹配
天数不足 / 超出
must-go 未安排
excluded 已进入行程
地点未定位
时间冲突
路线可能有问题
```

但这些大多属于 Advisory。

真正继续硬失败的主要是：

```text
数据结构损坏
无效实体引用
重复稳定 ID
权限 / Scope 越界
并发 generation / revision 冲突
非法 schema
安全边界
AI 伪造 Provider 事实
```

手工编辑不需要为了满足 AI 启发式而被自动重写。

---

# 11. 当前产品的主要复杂点

从用户体验看，当前五步已经可以完成完整规划，但存在几个明显的复杂点：

1. Step 2 的候选地点与 Step 3 的最终宏观路线是两层。
2. Step 3 的 Stay Block / stayDays 与 Step 5 的真实 Day 又是两层。
3. Step 4 新增详细地点后，还需要 Step 5 再把地点安排进具体 Day。
4. Macro Route 与 Detail Route 分别维护。
5. 上游修改需要通过 dependency / affectedDayIds 等机制同步到后续内容。
6. 用户高频调整最终行程时，需要在多个步骤之间切换。

这些是当前产品现状，不代表下一版仍要继续保持。
