# TravelPlanner 产品文档

> 状态：**当前产品需求最高依据**  
> 更新日期：2026-09-05  
> 本文件只定义产品逻辑、用户心智和交互规则，不定义数据结构、API、迁移、Prompt、组件或施工步骤。

---

# 1. 产品定位

TravelPlanner 是一个以 **最终线路 + 地图 + 右侧唯一控制台** 为核心的 AI 旅行规划工作台。

它不是“一次生成一篇攻略”的聊天机器人，也不应该让用户维护多套彼此同步的候选、粗行程和详细行程。

最高原则：

> **用户是旅行方案的唯一决策者。AI 负责生成、补充、解释和优化，但不能因为它认为“更合理”就擅自改掉用户已经排好的线路。**

系统可以提醒路线过长、时间紧张、地点未定位或安排不合理，但手工调整优先。只有用户明确要求 AI 优化时，AI 才获得对应范围内重新排列已有线路的权限。

---

# 2. 产品只保留两个核心工作区

顶层结构收敛为：

```text
规划：旅行需求
行程：最终线路
```

## 旅行需求

负责整趟旅行的基础输入，例如：

```text
日期 / 天数
出发地 / 结束地
人数
交通偏好
旅行节奏
主题与兴趣
限制条件
用户明确提出的地点或要求
```

## 最终线路

这是用户最主要、最高频的工作区。

原来的“地点推荐、路线和天数、补充景点、每日行程”不再拆成多个独立页面，而是都围绕同一份最终线路完成。

已有旅行再次打开时，默认应优先进入最终线路。

---

# 3. 最终线路是唯一的线路事实

用户看到的是一份始终保持顺序的地点列表：

```text
地点 A
↓
地点 B
↓
地点 C
↓
地点 D
...
```

一个地点可以是城市、景区、机场、酒店、餐厅、观景点、活动地点或其他真实地点。

用户不需要理解：

```text
Planning Area
Core Visit
Detail Interest
Backbone
Skeleton
Macro / Detail
Stay Block
```

最终线路负责表达：

```text
去哪些地点
地点顺序
哪些地点当前参与实际行程
哪里结束一天 / 形成住宿分界
地点之间如何移动
详细景点插在什么位置
```

地图、Day 和路线都从最终线路派生，不再成为另一套需要用户同步维护的计划。

---

# 4. 地点块统一

原“主要地点”和“详细景点”的地点卡都迁入最终线路，使用统一地点块表达。

地点块主要显示：

```text
地点名称
必要摘要
定位状态
当前状态
住宿 / 日程分界状态（如果适用）
```

右侧偏好按钮只保留：

```text
待定
不去
```

并继续保留：

```text
编辑
移除
```

不再要求普通用户维护“必去 / 想去 / 可选 / excluded”等多级偏好按钮。

“移除”和“不去”必须明确不同：

```text
不去 = 地点仍保留在最终线路及其排序中
移除 = 真正从最终线路删除
```

---

# 5. 地点状态：正常 / 待定 / 不去

最终线路里的地点有三个用户可理解的状态：

```text
正常
待定
不去
```

## 正常

- 正常显示。
- 参与当前日程和实际交通路线计算。

## 待定

- 地点块显示为深灰色。
- 仍保留在线性列表中的原排序位置。
- 地图仍显示。
- 不参与当前实际路线和 Day 的有效线路计算。

## 不去

- 使用与待定可明显区分的另一种深灰 / 弱化视觉。
- 仍保留在线性列表中的原排序位置。
- 地图仍显示。
- 不参与当前实际路线和 Day 的有效线路计算。

待定 / 不去恢复为正常后，地点直接在原位置重新参与线路，不需要 AI 再判断应该放在哪里。

---

# 6. 第一次生成：直接生成最终线路的主要地点骨架

最终线路为空时，用户可以：

```text
生成主要地点
```

这取代原来单独的“地点”页面。

AI 根据旅行需求生成主要住宿 / 停留地点、建议顺序和初始日程结构，并直接放入最终线路。

这些主要地点不是另一个候选池，不需要用户再进入下一步“采用”一次。

重要：

> **生成主要地点不代表每个地点默认住 1 晚。**

产品不存在“因为这个地点被生成，所以默认 stayDays = 1”这种规则。

---

# 7. 不存在“住几晚”的地点属性

地点上不维护：

```text
住 1 晚
住 2 晚
住 3 晚
```

这样的独立可编辑属性。

住宿的真正意义是：

> **在最终线路上形成一天结束的分界。**

如果同一个地点连续停留多日，产品直接用多个连续日程块表达，而不是给地点存一个“住几晚”的数字。

如果需要展示“连续住 2 晚”之类摘要，只能根据实际 Day 结果计算出来，不能成为另一份需要同步的数据。

---

# 8. 所有日程都是线性的

最终线路已经有明确顺序。

核心规则：

> **两个连续住宿分界之间的所有正常地点，都属于同一个 Day。**

例如：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦【住宿分界】
→ Wai-O-Tapu
→ 陶波
→ 惠灵顿【住宿分界】
```

自然得到：

```text
Day 1：奥克兰 → Hobbiton → 罗托鲁瓦
Day 2：罗托鲁瓦 → Wai-O-Tapu → 陶波 → 惠灵顿
```

系统不需要再问“这个地点归属哪一天”。它在线路里的位置已经决定了所属 Day。

即使某一天明显过长或不合理，也保留用户的手工结果。系统可以提醒，但不能自动拆分或重排。

---

# 9. 住宿操作：住 / 多一晚 / 不住

用户不编辑“住几晚”，而是直接调整线路上的日程分界。

## 住

把当前位置设为一天结束的住宿分界。

## 多一晚

直接增加一个新的日程块。

例如原来：

```text
Day 3：A → 陶波
Day 4：陶波 → B
```

用户在陶波增加一晚后：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

新增加的 Day 可以先没有详细地点，后续由用户手工添加或让 AI 补充。

## 不住

只取消当前地点的住宿分界，不删除这个地点，也不把它设为“不去”。

例如：

```text
Day 1：A → B【住】
Day 2：B → C → D【住】
```

把 B 改为“不住”后，机械变成：

```text
Day 1：A → B → C → D【住】
```

这里必须区分：

```text
不住 = 这个地点仍然去，只是不在这里结束一天
不去 = 这个地点暂时不参与实际线路，但仍保留在最终线路和地图中
```

---

# 10. 第一日、最后一日和连续停留

## 第一日

第一天从旅行起点开始，到第一个有效住宿分界结束。

起点可以是机场、城市、酒店、租车点或其他地点，不要求它本身是住宿点。

## 最后一日

最后一天允许没有住宿。

例如：

```text
皇后镇【上一晚住宿】
→ 箭镇
→ 皇后镇机场【旅行结束】
```

这就是最后一个 Day，不需要为了结构完整再制造一个住宿点。

## 连续停留

例如用户在陶波连续多一天，可以直接表现为：

```text
Day 3：A → 陶波
Day 4：陶波 → 陶波
Day 5：陶波 → B
```

以后 Day 4 加入详细地点后可以自然变成：

```text
Day 4：陶波 → Huka Falls → Tongariro → 陶波
```

Day 编号始终根据当前有效日程分界自动连续计算；用户改变分界后，编号跟着变化。

---

# 11. 手工排序是最高事实

所有地点块都可以保持明确顺序，并允许用户手工调整。

一旦用户修改顺序，当前顺序就是用户决定。

系统只做用户要求的那一个结构变化，不附带“智能修正”。

例如：

```text
拖动地点 = 只改变这个地点的位置
不住 = 只取消这个住宿分界
多一晚 = 只增加一个日程块
待定 = 只暂时退出实际路线
不去 = 只暂时退出实际路线
移除 = 只删除这个地点
```

AI 不能因为地理上更合理、一天太长或路线绕路，就自动把用户线路改回去。

只有用户明确调用：

```text
优化这一天
优化这一段
优化全程
```

AI 才可以在对应范围内重新排列已有线路。

---

# 12. 第二次生成：在最终线路里生成详细地点

主要地点和初始日程已有后，用户在同一最终线路页面点击：

```text
生成详细地点
```

这取代原来独立的“补充景点”页面。

AI 生成景点、活动、观景点、餐厅等详细地点，并直接插入最终线路。

例如原来：

```text
奥克兰
→ 罗托鲁瓦【住】
→ 陶波【住】
```

生成后可以成为：

```text
奥克兰
→ Hobbiton
→ 罗托鲁瓦【住】
→ Wai-O-Tapu
→ Huka Falls
→ 陶波【住】
```

详细地点一旦插入最终线路，就自然属于对应 Day，不再需要另一个“生成每日行程”的步骤进行二次搬运。

---

# 13. AI 自动插入新地点的权限边界

生成详细地点时，AI可以决定：

> **新地点插在哪两个已有地点之间。**

但不能借机：

```text
交换已有地点的相对顺序
删除已有地点
改变已有地点状态
改变已有住宿分界
把已有地点搬到另一个 Day
```

例如原线路：

```text
A → B → C → D
```

新增 X 后可以是：

```text
A → X → B → C → D
A → B → X → C → D
A → B → C → X → D
```

但不能因为加入 X 而变成：

```text
A → C → X → B → D
```

除非用户明确要求 AI 优化。

详细地点生成也可以只针对某个 Day、某一段线路或某个住宿地点附近局部执行；其他部分保持不动。

---

# 14. 地图、定位和路线只根据最终线路更新

定位和线路生成的产品输入只来自：

> **当前最终线路列表。**

只要最终线路发生变化，相关地图和线路展示就自动更新，不要求用户再执行一次“同步”或“重新生成整条路线”。

典型变化包括：

```text
生成主要地点
新增地点
生成 / 插入详细地点
编辑地点
移除地点
拖动排序
正常 ↔ 待定
正常 ↔ 不去
住宿分界变化
增加日程块
交通方式变化
```

规则：

- 所有仍在最终线路列表中的地点都属于地图展示对象。
- 正常、待定、不去都在地图上显示，并用不同颜色 / 状态区分。
- 只有正常地点参与当前实际交通路线计算。
- 待定 / 不去地点不参与路线，但保留地图标记和列表位置。
- 地点定位失败时仍保留地点，不自动删除、不自动补位。
- 距离、时间、路线 geometry 等地图事实只能使用地图 Provider 返回的真实结果。

例如：

```text
A
X（待定）
B
Y（不去）
C
```

地图显示 A、X、B、Y、C 五个地点，但当前实际路线按：

```text
A → B → C
```

计算。

---

# 15. 页面与交互入口

桌面端继续以：

```text
地图 / 日程 / 路线展示
+
右侧唯一控制台
```

作为主要结构。

地图和日程主体负责：

```text
展示
选择
聚焦
```

右侧控制台负责业务动作，例如：

```text
生成主要地点
生成详细地点
待定 / 不去
编辑 / 移除
住 / 多一晚 / 不住
交通方式
定位修复
AI 优化
```

同一个业务动作只有一个主要入口。地图 Popup 不再变成第二套编辑器。

任意时刻尽量只保留一个最主要的 Primary CTA，其他动作作为次级操作。

---

# 16. AI 和用户控制权

AI 默认可以：

```text
根据旅行需求生成主要地点和初始线路
生成详细地点并插入线路
解释风险和不合理之处
提出优化建议
在用户明确授权的范围内优化线路
```

AI 默认不能：

```text
因为“更合理”改掉用户手工排序
静默删除用户地点
自动恢复待定 / 不去地点
为了加入新景点重排已有地点
擅自改变住宿分界
擅自把一天拆成两天或把两天合并
```

产品允许保存不完整、不合理、未定位或暂时矛盾的旅行方案；这些问题通过提示、建议和用户主动的 AI 优化解决。

---

# 17. 增量变化原则

没有受到变化影响的线路内容保持不动。

例如：

```text
新增详细地点
→ 只插入新地点，不重做整趟旅行

地点设为待定 / 不去
→ 跳过该地点重新计算当前路线，但保留地点和排序

取消住宿分界
→ 机械合并由该分界切开的相邻日程

多一晚
→ 只新增对应日程块，不自动从前后搬景点
```

需要重新排列已有内容时，必须由用户明确触发 AI 优化。

---

# 18. 用户完整心智

```text
填写旅行需求
↓
进入最终线路
↓
生成主要住宿 / 停留地点和初始日程结构
↓
手工调整顺序、住宿分界、待定 / 不去
↓
生成详细地点
↓
详细地点直接插入最终线路和对应 Day
↓
继续手工调整
↓
需要时让 AI 优化某一天 / 某一段 / 全程
```

用户始终只是在维护同一份最终线路。

# 19. 产品验收原则

最终产品至少满足：

```text
只有“旅行需求”和“最终线路”两个核心工作区
原地点页和补充景点页不再独立存在
粗路线和每日详细行程不再维护两套计划
最终线路是一份始终保序的地点列表
待定 / 不去仍留在线路列表和地图中，但不参与当前路线
地点块主偏好只保留“待定 / 不去”，并保留编辑 / 移除
生成主要地点不默认每个地点住 1 晚
不存在“住几晚”的地点属性
住宿分界直接切出 Day
两个住宿分界之间的所有正常地点属于同一天
手工不合理也允许，AI 不自动修正
生成详细地点后直接进入最终线路
自动插入新地点不改变已有地点相对顺序
最终线路一变化，定位、地图和路线自动跟随更新
地图显示正常 / 待定 / 不去全部地点并区分视觉
只有正常地点参与实际路线计算
右侧控制台仍是唯一业务操作入口
```
