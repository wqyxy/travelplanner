# TravelPlanner 产品文档

> 状态：**当前产品现状**  
> 更新日期：2026-09-05  
> 本文件只描述当前 `main` 上用户实际面对的产品结构和行为。

---

# 1. 产品定位

TravelPlanner 是一个以 **地图展示 + 右侧唯一操作区 + AI 辅助规划** 为核心的旅行工作台。

当前产品已经从旧五步流程收敛为两个工作区：

```text
规划 · 旅行需求
行程 · 最终线路
```

用户真正维护的旅行路线只有一份：**最终线路**。

```text
旅行需求
→ 最终线路
→ 自动得到 Day
→ 自动得到地图路线
```

AI 可以帮助发现地点、补充详细地点和提出优化建议，但用户始终是最终决策者。

---

# 2. 工作区一：旅行需求

“规划 · 旅行需求”负责整趟旅行的基础约束，例如：

```text
目的地 / 出发地
日期 / 天数
人数
交通偏好
旅行节奏
主题和兴趣
预算与限制
其他自然语言要求
```

这些信息是 AI 研究和路线建议的输入。

用户可以先只填写部分需求，也可以后续继续修改。系统可以提醒下游内容可能需要重新确认，但不会因为“旅行经验上不够合理”而擅自改掉用户线路。

---

# 3. 工作区二：最终线路

“行程 · 最终线路”是旅行规划的主要工作区，也是用户交互最多的区域。

最终线路是一条有顺序的地点链：

```text
A
→ B
→ C
→ D
```

每个地点在线路中是一次独立出现，因此同一个现实地点可以出现多次。

例如多住一晚：

```text
A
→ 陶波 #1【住】
→ 陶波 #2【住】
→ B
```

两个“陶波”引用同一个现实地点，但拥有不同的线路节点 ID。

---

# 4. 用户可以直接修改什么

所有线路业务操作统一放在右侧最终线路区域。

用户可以：

```text
手工添加地点
删除某一次线路出现
拖动排序 / 上移 / 下移
设置正常 / 待定 / 不去
设置住 / 不住 / 多一晚
设置到达当前地点的交通方式
编辑地点名称和类型
重新识别地点
粘贴 Google Maps 链接
从右侧进入地图选点模式
```

地图本身不提供第二套删除、状态、住宿或优化按钮。

---

# 5. 地点状态

每个最终线路节点只有三种状态：

```text
normal     正常
tentative  待定
no_go      不去
```

`tentative` 和 `no_go` 的含义是：

- 节点仍保留在线路原位置；
- 已定位时仍显示在地图上；
- 原来的住宿分界仍保存；
- 原来的“到达这里的交通方式”仍保存；
- 暂时不参与当前 Day 和交通路线；
- 恢复 normal 后，原位置和原设置重新生效。

只有“从线路移除”才真正删除这一次线路节点。

---

# 6. 住 / 不住 / 多一晚

`住` 表示当前 normal 节点成为一天的结束位置。

```text
endsDay = true
```

`不住` 只取消这个日程分界：

```text
endsDay = false
```

它不会删除地点、不会移动后面的地点，也不会自动挑另一个住宿点。

`多一晚` 会在当前位置后新增一个引用同一 Place 的独立线路节点。

系统不使用“某地点 stayDays=2”作为用户需要维护的核心概念。

---

# 7. Day 是自动得到的

用户不需要维护第二份 Day 路线。

系统根据：

```text
旅行起点
+ normal 最终线路节点
+ 当前生效的 endsDay
```

自动得到 Day。

修改：

```text
顺序
状态
住 / 不住
多一晚
```

之后，Day 编号和日期会重新计算。

最后一个 normal 节点即使没有“住”，也可以形成合法的最后一天。

---

# 8. 到达交通

交通属于“到达当前节点”，而不是属于两个地点之间一份独立可漂移的数据。

例如：

```text
A —drive→ X —walk→ B
```

如果 X 暂时变成待定：

```text
A —walk→ B
```

恢复 X 后仍然是：

```text
A —drive→ X —walk→ B
```

最终线路只保存用户选择的交通方式。

真实路线的：

```text
距离
时长
geometry
```

必须来自 Route Provider，不能由 AI、UI 或 API 调用方伪造。

---

# 9. AI：生成主要地点

当最终线路为空时，用户可以点击：

```text
生成主要地点
```

AI 会根据旅行需求研究整趟旅行最重要的地点，并给出本轮建议顺序。

结果会**直接进入最终线路**，不再先进入一个用户需要维护的候选地点页面。

AI 可以对本轮新增节点建议：

```text
顺序
是否作为一天结束位置
到达交通方式
```

但：

- 不存在“每个生成地点默认住 1 晚”的规则；
- AI 不确定住宿分界时可以全部不设；
- 已经存在最终线路后，普通“生成主要地点”不能覆盖用户线路。

---

# 10. AI：生成详细地点

最终线路存在后，用户可以：

```text
生成全程详细地点
补充某一天的详细地点
补充指定连续线路段的详细地点
```

详细地点可以是：

```text
景点
观景点
活动
餐厅
其他真实旅行地点
```

普通详细地点生成只有一个权限：**插入新节点**。

它不能：

```text
重排已有节点
删除已有节点
改变 normal / tentative / no_go
改变已有住宿分界
把已有节点移动到其他 Day
```

也就是说：

```text
原线路：A → B → C
AI 新增：X / Y
```

允许：

```text
A → X → B → Y → C
```

不允许普通生成偷偷变成：

```text
C → A → X → B
```

---

# 11. AI：显式优化

只有用户明确点击优化时，AI 才获得重排已有节点的权限。

当前入口：

```text
优化这一天
优化这一段
优化全程
```

优化范围由系统在服务端明确计算。

AI 只能重排授权范围内已经存在的 normal 线路节点，不能新增、删除或替换节点。

`tentative / no_go` 不属于可移动集合，仍保持原线路槽位。

优化完成后不会直接覆盖用户线路，而是出现一份方案：

```text
采用这个顺序
不采用
```

采用后，如果没有继续修改旅行，还可以撤销这次优化。

---

# 12. 地图

地图负责：

```text
显示所有已定位最终线路节点
显示 normal 节点形成的当前路线
选择 / 聚焦地点
辅助人工定位
```

normal / tentative / no_go 会使用不同视觉状态。

如果某节点 inactive 后，旧 Provider route geometry 已经不符合当前 Day，地图不会继续显示经过这个 inactive 节点的旧线路。

路线暂时重算失败不会回滚已经保存的最终线路。

---

# 13. 未定位地点

地点可以先保存、后定位。

如果 Provider 暂时没有找到可靠位置：

- 地点仍保留在线路；
- 不自动删除；
- 不自动补位；
- 不导致整条规划失败；
- 用户可以重新识别；
- 用户可以粘贴 Google Maps 链接；
- 用户可以从右侧进入地图选点。

系统不能为了“地图上必须有点”而伪造坐标。

---

# 14. 用户控制原则

当前产品的核心原则是：

> **用户是旅行方案的唯一决策者，AI 只提供研究、提醒和可撤销建议。**

系统可以提醒：

```text
日期可能不匹配
路线可能绕路
地点未定位
当天安排可能很满
交通路线暂时算不出来
```

但普通旅行合理性问题不能成为系统擅自修改用户方案的理由。

真正应该硬失败的主要是：

```text
数据结构损坏
实体引用无效
稳定 ID 冲突
Scope / AI 权限越界
generation / Revision 并发冲突
非法 Schema
安全边界
伪造 Provider 事实
```

---

# 15. 当前界面不再存在的用户职责

下面这些概念仍可能作为内部代码或兼容结构暂时存在，但已经不是正常用户工作流：

```text
独立 Candidate 候选页面
独立 Skeleton / stayDays 页面
独立“补充景点”步骤
独立 Day / Stop 路线编辑步骤
五步导航
```

用户不需要理解这些内部结构，也不需要在多个步骤之间来回同步同一趟旅行。
