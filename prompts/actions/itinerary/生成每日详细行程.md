# 生成每日详细行程

目标：根据当前 Step 3 路线、已有 Candidate 和用户偏好，为目标 Day 生成 Stop 级详细安排。

原则：
- 当前 canonical 属于用户。已有 Day、Anchor、Candidate、preference 和用户明确要求优先于一般旅行经验。
- 尽量让每天节奏合理、路线顺畅、避免明显时间冲突，并优先安排 `must_go` / `want_to_go`，但这些是规划质量目标，不是拒绝条件。
- `excluded` 默认不要主动加入；如果用户明确要求安排它，可以安排并保留该 preference。
- 未定位 Candidate 可以进入日程。不要因此跳过用户明确指定地点，也不得伪造坐标、Provider ID、距离、路线 geometry 或 Provider 时长。
- Candidate 暂无 Planning Area parent 时仍可安排；不要为满足层级规则虚构 parent。
- Place.kind 不决定它能否成为 Stop；是否适合作为当天活动由用户意图和 planningRole/语境共同决定。
- 时间允许不完整：可只给 `scheduleText`（如“上午”“到达后”“次日凌晨”），也可给 startTime/endTime/duration 的任意有把握部分。
- 不确定精确时间时宁可留 null 或使用 scheduleText，不要编造精确时刻。
- startTime/endTime 可能表示跨夜；不要仅因 endTime <= startTime 就拒绝。
- duration 与时刻不完全一致时不要为了通过校验偷偷改数字；保留最可信信息。
- 如果安排存在重叠、未覆盖 must_go、未定位等问题，可以保留并在 assistantMessage 中说明建议。
- 不修改目标 Day 之外的内容；不要为了“让整趟更合理”顺手调整其他日期。
- 只有 Scope 越界、引用不存在、结构无法成立、安全边界或 Provider 事实伪造时才应失败。

输出：只返回 `itinerary.detail.generate.output` 对应 JSON。
