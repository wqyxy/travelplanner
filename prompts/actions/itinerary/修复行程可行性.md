# 优化这一段或全程

目标：只有用户明确点击“优化这一段”或“优化全程”时，对服务端给出的授权最终线路节点提出重排建议。

这是显式优化动作。普通地点生成没有这项权限。

你会收到：
- `optimizeScope`：`segment` 或 `trip`；
- `targetNodeIds`：本轮唯一允许改变相对顺序的 normal 最终线路节点；
- 当前 finalRoute 节点、Place 信息、派生 Day 和已有 Provider 路线事实。

输出合同仍使用 `itinerary.repair.output` 的 Day 数组作为结构化承载格式，但服务端只会读取其中现有线路节点 ID 的相对顺序，不会接受你对 Day 字段本身的修改。

要求：
- 只允许重排 `targetNodeIds` 中已有节点。
- 必须保留 `targetNodeIds` 的完整集合，不能新增、删除、替换或伪造节点 ID。
- target 范围之外的节点视为固定锚点，不得越过或移动。
- tentative / no_go 不属于本轮可移动集合，必须保持原位置。
- 不得修改任何节点的 status、endsDay、Place、交通设置或详细字段。
- 如果范围内存在住宿分界节点，节点携带的 endsDay 不变；你只能建议节点顺序。
- 可以参考 Provider 已有路线事实、用户偏好和旅行要求来减少绕路，但用户明确约束优先。
- 未定位地点仍必须保留，不能因为缺少路线事实而删除。
- 不得伪造坐标、真实距离、真实时长或 route geometry。
- `days` 中可以保留当前 Day 的其他只读字段；服务端最终只应用授权节点的顺序变化。
- 如果当前顺序已经合适，可以返回与现状相同的节点顺序。

输出：只返回 `itinerary.repair.output` 对应 JSON。
