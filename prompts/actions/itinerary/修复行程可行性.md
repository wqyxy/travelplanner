# AI 排序：全程或区段

目标：只有用户明确启动排序后，才对授权范围内的最终线路地点提出新顺序。

## 全程 AI 排序

当输入包含 `organizer` 时，它是本动作的主要排序上下文：
- `organizer.blocks` 是现有日程块；Block 本身及其顺序不能新增、删除或改名。
- `organizer.blocks[].places` 中每一项都只是一个地点。不要区分城市、景点、餐厅或其他类型；进入这里以后全部按同一种 Place 处理。
- 可以把普通 Place 从一个 Block 移动到另一个 Block，也可以改变 Block 内顺序。
- 每个 Block 的 `fixedEndPlaceId` 是住宿/日终边界，必须留在原 Block 最后，不参与跨 Block 移动。
- 所有输入 Place 必须且只能出现一次；不得新增、删除、替换、修改 ID 或名称。
- 用户的 `parameters.request` 优先；如果只是自动排序，则综合旅行合理性、已有 Provider 路线事实、减少绕路和往返、每日安排自然程度来排序。

输出合同仍使用 `itinerary.repair.output` 的 `days` 承载结果：
- `days` 必须按 `organizer.blocks` 原顺序完整返回；Day ID 必须对应 Block ID。
- 每个 Day 的 `stops` 按该 Block 新的 Place 顺序返回；对应 `fixedEndPlaceId` 的 Day 节点保持日终位置。
- 服务端会把返回结果重新转换成 `{ blocks: [{ id, places: [{ id, name }] }] }` 并严格校验，再生成最终线路移动命令。

## 区段兼容模式

如果没有 `organizer`，则这是旧的区段优化：只允许重排 `targetNodeIds`，范围外节点不得越过或移动。

## 通用限制

- 不得修改 status、endsDay、Place 内容、交通设置、活动、时间或其他详细字段。
- tentative / no_go 不属于可移动集合，保持原位。
- 未定位地点仍必须保留。
- 不得伪造坐标、真实距离、真实时长或 route geometry。
- 当前顺序已经合理时，可以返回等价顺序。

只返回 `itinerary.repair.output` 对应 JSON。
