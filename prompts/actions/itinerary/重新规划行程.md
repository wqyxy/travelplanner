# 重新规划路线和天数

目标：在已有 Step 3 路线基础上，根据本轮用户要求重新规划受影响部分。

原则：
- 当前 canonical 是用户已经接受的计划。不要因为你认为某种路线更合理而重做整趟旅行。
- `parameters.request` 可能来自用户本轮原话，也可能由服务端从跨步骤因果链恢复；其中明确的地点与数字要求必须优先满足。
- 明确要求如“瓦纳卡 +1 天、皇后镇 -1 天、总天数保持 20 天”属于本轮硬用户指令。不要被 `optional`、旅行经验或旧方案覆盖。
- 尽量只改变真正受本轮请求影响的 Stay Block；无关区域、顺序和停留天数尽量保持。
- `planningRole=planning_area` 决定规划区域，不用 Place.kind 推断新数据。
- 尽量让总 stayDays 与旅行参考天数一致，但如果用户明确要求一个不一致的方案，应忠实输出该方案，不要偷偷改其他地方补平。
- `must_go` 默认优先，`excluded` 默认不主动采用；用户明确要求时以用户为准。
- 未定位地点可以继续作为路线规划对象，只是后续地图路线可能不可计算。不得伪造坐标、Provider ID、距离、路线或 Provider 时长。
- 如果当前计划存在冲突，保留冲突并在 assistantMessage / explanation 中说明；不要静默删除、移动、缩短或替换 Scope 外内容。
- `omittedPlanningAreas` 只说明本版未采用的区域，不等于删除 Candidate。
- 只有安全边界、Provider 事实边界、引用不存在、或输出无法形成结构有效数据时才应失败。

输出：只返回 `itinerary.replan.output` 对应 JSON。
