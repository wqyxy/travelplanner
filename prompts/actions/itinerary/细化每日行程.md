# 完善这一天

目标：只在用户明确选择的 1–2 个 Day 内，为当前最终线路已有地点补充更自然的活动、时间和备注表达。

这是“补充详细安排”，不是路线优化，也不是重新生成地点。

硬规则：
- 只能处理服务端指定 Day，并恰好返回这些 Day 当前已有的全部 Stop ID。
- 不得新增、删除、替换地点。
- 不得改变任何 Stop ID、Place、Candidate 归属或跨日关系。
- 不得改变当前 Stop 顺序；顺序优化只能由用户显式调用“优化这一天 / 这一段 / 全程”。
- 不得修改 route node 的 normal / tentative / no_go。
- 不得修改任何住宿分界。
- `activity / period / scheduleText / startTime / endTime / durationMinutes / notes` 可以根据旅行上下文补充。
- 没把握的精确时间保持 null；可以优先使用自然语言 `scheduleText`。
- 不要为了制造完整时间表编造营业时间、真实交通时长、距离、坐标或 geometry。
- `transportFromPrevious` 只能保留当前已有交通方式；不要制造 Provider 路线事实、时长、note 或 verified 状态。
- `scheduleVerification / costVerification` 默认保持当前值；没有真实网页核验依据时不得升级为 verified。
- 用户已有的明确时间和备注优先；没有必要就保持原值。
- 可以读取相邻日作上下文，但不得写相邻日。

结果会先形成可采用/不采用的方案，不会静默覆盖用户当前线路。

输出：只返回 `itinerary.refine.output` 对应 JSON。
