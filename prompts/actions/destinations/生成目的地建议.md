# 生成目的地建议

目标：根据用户当前旅行需求，生成 Step 2 的愿望清单候选，包括 Planning Area 与必要的 Core Visit。

规划角色：
- `planning_area`：用户可能用来组织路线、住宿、交通或连续停留的规划区域。
- `core_visit`：会明显影响路线或日程容量的重要游览地，但不一定住宿。
- 不在本动作生成普通 `detail_interest`；普通景点留给 Step 4。

核心原则：
- `Place.kind` 描述现实世界地点类型，`planningRole` 描述它在本次旅行中的规划用途，两者完全独立。
- Planning Area 不要求 `kind=city`。城市、岛屿、自然景区、机场、港口、车站等，只要用户确实会用它组织路线，都可以成为 `planning_area`。
- Core Visit 也不禁止 `kind=city`；是否属于 core_visit 看它在本次旅行里的日程意义。
- 每个 Candidate 必须显式给出 planningRole，不要依赖 Place.kind 让服务端猜。
- Core Visit 可以绑定一个 Planning Area，也可以在暂时无法合理归类时 `planningAreaCandidateId = null`；不要为满足层级规则虚构 parent。
- `must_go / want_to_go / optional / excluded` 是用户偏好，不是 Candidate 是否可存在的权限规则。本轮新建议默认保持合同要求的 preference，不要擅自替用户标记必去或排除。
- 不要因为名称相似而静默删除建议；语义重复由服务端 Advisory 提醒用户决定。
- 尽量给出数量适中、真正会影响旅行决策的地点，不追求凑数量。
- 如果用户已有明确地点或限制，优先保留并围绕它们提出建议，不要为了旅行经验偷偷改掉用户意图。
- 可以使用允许的公开网页研究旅行语义，但不得把来源链接、引用列表、坐标、Provider Place ID、路线 geometry、Provider 距离或 Provider 时长写入结构化结果。
- 不生成 Day / Stop，不声称已经写入 canonical。

输出：只返回 `destination.generate.output` 对应 JSON。
