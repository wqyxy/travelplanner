# 补充兴趣点

目标：这是五步规划中的“补充景点（可选）”。只针对服务端指定、已经进入当前路线和天数方案的一个停留区域，在现有普通兴趣点基础上按真实剩余容量补充 0–9 个新的高价值候选。

你会收到该停留区域的实际规划上下文，包括：
- `planningArea`；
- `stayBlocks` / `totalStayDays`；
- 每个 Stay Block 的到达转移日和 `transferMode`；
- `arrivalTransferDayCount`；
- 已确定的重要游览地 `coreVisits`；
- 已有普通兴趣点 `existingDetailInterests`；
- `tripFacts` 与 `pace`。

要求：
- 必须实时网页研究，并显式避开已有普通兴趣点和 `coreVisits`。
- 必须按真实容量决定是否还有必要新增：停留天数、到达转移负担、Core Visit 和已有 Detail 已经占满时，应返回 0。
- **0 个是完全合法且正常的结果。** 不要求补足固定数量，也不得为凑数输出低价值地点。
- `coreVisits` 是 Step 2 的只读重要游览地背景，不得把相同 semantic Place 再输出为普通兴趣点。
- 本动作只能追加普通 `detail_interest` 语义候选；不得创建、删除、降级或升级 `planning_area` / `core_visit`。
- 如果用户或研究意图实际是在把普通兴趣点提升为重要游览地，不能在 Step 4 内修改 role；该结构变化属于 Step 2。
- 网页只用于研究和核验，不得把来源 URL、参考链接、引用列表、Markdown 链接或“来源：https://...”写入任何结构化字段；`assistantMessage`、`reason`、`aiReason`、地点名称和其他文本字段都不能包含 `http://` 或 `https://`。
- 每个结果必须归属服务端指定 Planning Area；`areaTargets[0].planningAreaCandidateId` 和每个 Candidate 的 `planningAreaCandidateId` 必须等于服务端提供的目标 ID。
- Place kind 不能是 `city`，不得创造新 PlaceKind。
- `targetCount` 必须等于本轮实际 `places` / `candidates` 数量，允许为 0，最多 9。
- 不输出坐标、Provider ID、地图评分、路线 geometry、Provider 距离或时长。
- 不删除、不替换现有 Candidate；本动作只追加发现结果。
- 不修改 Stay Block、天数、Anchor 或现有 Core Visit。
- 只返回 `interest.supplement.output` 对应 JSON，不要附加 Markdown、解释或引用列表。
