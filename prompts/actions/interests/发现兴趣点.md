# 发现兴趣点

目标：这是五步规划中的“补充景点（可选）”。只针对服务端指定的一个 Planning Area，根据当前可用上下文研究本轮 0–9 个值得加入候选池的普通 `detail_interest`。

你会收到该 Planning Area 的规划上下文，包括：
- `planningArea`；
- `planningAreaAdopted`：当前是否已经进入 Step 3 路线；
- `stayBlocks` / `totalStayDays`；
- 每个 Stay Block 的到达转移日和 `transferMode`；
- `arrivalTransferDayCount`；
- 已确定的重要游览地 `coreVisits`；
- 已有普通兴趣点 `existingDetailInterests`；
- `tripFacts` 与 `pace`。

要求：
- 必须实时网页研究；AI 自主决定实际新增数量，不为凑数输出低价值地点。
- 如果 `planningAreaAdopted = true`，优先结合真实停留天数、到达转移负担、已有 Core Visit 与 Detail Interest 判断容量。
- 如果 `planningAreaAdopted = false` 或尚无 Stay Block，不要把 `totalStayDays = 0` 理解为“不允许研究”。此时按用户旅行需求、区域价值、pace 与已有候选做更保守的候选研究，等待 Step 3/5 后续决定是否采用。
- **0 个是完全合法且正常的结果。** 如果已有候选已经足够，就返回 0，不得为了“看起来有结果”硬凑地点。
- `coreVisits` 是 Step 2 已确认的重要游览地，本步骤只把它们作为背景；不得把同一 semantic Place 再次作为普通详细兴趣点输出。
- 本步骤只能产生普通 `detail_interest` 语义候选，不得创建或提升 `planning_area` / `core_visit`。如果研究发现某个地点更适合成为 Core Visit，也不要在本动作中改 role；该结构变化属于 Step 2。
- `Place.kind` 只描述现实世界地点类型，不决定 planningRole；允许使用现有任意 Place kind，包括 `city`，不得创造新 PlaceKind。
- 网页只用于研究和核验，不得把来源 URL、参考链接、引用列表、Markdown 链接或“来源：https://...”写入任何结构化字段；`assistantMessage`、`reason`、`aiReason`、地点名称和其他文本字段都不能包含 `http://` 或 `https://`。
- 每个结果必须绑定服务端指定 Planning Area；`areaTargets[0].planningAreaCandidateId` 和每个 Candidate 的 `planningAreaCandidateId` 必须等于服务端提供的目标 ID。这是本次按区域研究的 Action Scope，不代表 canonical 永久要求所有 detail_interest 都必须有父级。
- `targetCount` 必须等于本轮实际 `places` / `candidates` 数量，允许为 0，最多 9。
- 不输出坐标、Provider ID、Provider 评分、路线 geometry、Provider 距离或时长。
- 地图定位成功与否不决定兴趣点能否先进入候选池；定位由服务端后续处理。
- 不修改 Stay Block、天数、Anchor 或现有 Core Visit。
- 只返回 `interest.discover.output` 对应 JSON，不要附加 Markdown、解释或引用列表。
