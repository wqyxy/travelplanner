# 发现兴趣点

目标：这是五步规划中的“补充景点（可选）”。只针对服务端指定、已经进入当前路线和天数方案的一个停留区域，根据真实可用容量研究本轮 0–9 个值得加入候选池的普通详细兴趣点。

你会收到该停留区域的实际规划上下文，包括：
- `planningArea`；
- `stayBlocks` / `totalStayDays`；
- 每个 Stay Block 的到达转移日和 `transferMode`；
- `arrivalTransferDayCount`；
- 已确定的重要游览地 `coreVisits`；
- 已有普通兴趣点 `existingDetailInterests`；
- `tripFacts` 与 `pace`。

要求：
- 必须实时网页研究；AI 自主决定实际新增数量，不为凑数输出低价值地点。
- 必须先考虑真实容量：停留天数越少、到达转移负担越重、已有重要游览地占用越多，新增普通兴趣点应越少。
- **0 个是完全合法且正常的结果。** 如果当前容量、已有 Core Visit 或已有兴趣点已经足够，就返回 0，不得为了“看起来有结果”硬凑地点。
- `coreVisits` 是 Step 2 已确认的“重要游览地”，本步骤只把它们作为容量背景；不得把同一地点再次作为普通详细兴趣点输出。
- 本步骤只能产生普通 `detail_interest` 语义的候选，不得创建或提升 `planning_area` / `core_visit`。如果研究发现某个普通兴趣点其实应升级为重要游览地，也不要在本动作中改 role；该结构变化属于 Step 2。
- 网页只用于研究和核验，不得把来源 URL、参考链接、引用列表、Markdown 链接或“来源：https://...”写入任何结构化字段；`assistantMessage`、`reason`、`aiReason`、地点名称和其他文本字段都不能包含 `http://` 或 `https://`。
- 每个结果必须绑定服务端指定 Planning Area；`areaTargets[0].planningAreaCandidateId` 和每个 Candidate 的 `planningAreaCandidateId` 必须等于服务端提供的目标 ID。
- 允许所有非 `city` 的现有 Place kind；不得创造新 PlaceKind，也不得输出 `city` Place。
- `targetCount` 必须等于本轮实际 `places` / `candidates` 数量，允许为 0，最多 9。
- 不输出坐标、Provider ID、Provider 评分、路线 geometry、Provider 距离或时长。
- 地图定位成功与否不决定兴趣点能否先进入候选池；定位由服务端后续处理。
- 不修改 Stay Block、天数、Anchor 或现有 Core Visit。
- 只返回 `interest.discover.output` 对应 JSON，不要附加 Markdown、解释或引用列表。
